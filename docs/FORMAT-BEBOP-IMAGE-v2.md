# Формат образу bebop, контейнер версії 2 — нормативний опис

Статус: **нормативний**, заморожено 2026-10-27 (лейн W-ES-P0, фаза P0 плану
`docs/research/R-EMBED-STORE-2026-10-27.md`). Документ описує байти, які сьогодні пишуть і
читають `crates/bebop-store` (Rust), `bebop-lang/selfhost/prelude/store.bp` + `selfhost/std/kv.bp`
(bebop), `crates/bebop-wasm` (wasm32) і `crates/bebop-wasm/oracle.py` (Python). Там, де код і
старі документи розходяться, **правий код, що читає й пише живі образи**; розбіжність названо в §11.

Ключові слова: **МУСИТЬ** — порушення робить образ невалідним або читача неконформним;
**НЕ МУСИТЬ** — заборона; **МОЖЕ** — дозволено. Ідентифікатори — англійською, як у коді.

Константи цього документа (§10) читає тест
`crates/bebop-store/src/format/tests.rs::the_format_document_states_every_constant_with_the_codes_value`:
змінити значення тут або в коді без іншого боку — червоний тест.

## 1. Комірка, порядок байтів, нуль

- Образ — послідовність **комірок** по 8 байт; комірка — `i64` **little-endian**. Усі індекси,
  довжини й зміщення в образі — у комірках, якщо не сказано «байт».
- Хвіст образу, коротший за 8 байт, **ігнорується** (не доповнюється): обрізаний образ не
  може стати валідним.
- Читач, який читає комірку за кінцем образу, МУСИТЬ отримати **0** — це вже null формату
  (`ref` 0 = немає об'єкта, довжина 0 = немає payload). Читач НЕ МУСИТЬ панікувати чи
  алокувати за значенням з образу, не обмеживши його образом (`lib.rs` `Cells::cell_at`,
  `obj_cells`, `follow`).

## 2. Розкладка образу

| Комірки | Байти | Що |
|---|---|---|
| 0..15 | 0..127 | суперблок A |
| 16..36 | 128..295 | PartTab, названий суперблоком A (його пише коміт **з** B, що пише A) |
| 512..527 | 4096..4223 | суперблок B |
| 528..548 | 4224..4391 | PartTab, названий суперблоком B (його пише коміт з A) |
| 1024.. | 8192.. | арена: bump-алокатор самоописних об'єктів, лише дописується |

Решта комірок сторінок 0 і 1 — нулі. Кожен PartTab лежить на сторінці **свого** суперблока,
а два послідовні покоління (суперблок + PartTab) — на **різних 4 KiB-сторінках**, тож розрив
однієї сторінки не руйнує обидва покоління. Суперблок (128 байт)
і PartTab (168 байт) кожен уміщується в перші 512 байт своєї сторінки; чи це один атомарний
сектор на конкретній ФС — **не перевірено**, тому єдиний аргумент цілісності — crc (§6).

## 3. Суперблок (16 комірок, `SB_CELLS`)

| Комірка | Ім'я (`format.rs`) | Значення |
|---|---|---|
| 0 | magic | `MAGIC` = «BEBOPST1» як LE `i64` |
| 1 | `SB_VERSION` | версія контейнера, `FORMAT_VERSION` = 2 (усі письменники) |
| 2 | `SB_GEN` | генерація; свіжий образ = 0, кожен коміт +1 |
| 3 | `SB_PARTTAB` | **абсолютний індекс PartTab** (не корінь даних!); 0 = порожній образ без кореня |
| 4 | `SB_USED` | `arena_used`: абсолютний індекс першої комірки за останнім об'єктом; свіжий = 1024 |
| 5 | `SB_PROJTAB` | таблиця проєкцій (DG5), 0 = немає; коміт, що про неї не знає, переносить її |
| 6 | `SB_MIGRATION` | таблиця міграцій (bebop T114), 0 = немає; переноситься незмінною |
| 7 | `SB_LIVE` | живі комірки (заголовки включно) |
| 8 | `SB_SUPERSEDED` | витіснені комірки з останньої компакції (пишеться з W-CRC/W-DELTA) |
| 9 | `SB_ANC` | **якір** останнього коміту (§7); 0 = якоря немає |
| 10 | `SB_COMMIT` | bebop C3: ref на commit-об'єкт (`st_sb_write_ch`); Rust пише 0 |
| 11 | `SB_HEADS` | bebop C3: ref на таблицю heads; Rust пише 0 |
| 12 | `SB_CAPACITY` | ємність арени в комірках, рахуючи від 1024 |
| 13, 14 | — | **МУСЯТЬ бути 0** (S-1; oracle.py відмовляє статусом 5) |
| 15 | `SB_CRC` | zlib crc32 комірок 0..14 (§6), збережений як невід'ємний `i64` |

**Валідний суперблок**: комірка 0 = `MAGIC` **і** `(комірка 15) as u32` = crc32(комірки 0..14)
**і** усі 16 комірок є в образі.

### 3.1 Вибір живого суперблока (`format::pick_checked_in`)

1. Валідні — за правилом вище. Обидва валідні → більша генерація; рівні → A. Один → він.
   Жодного → `PickError::NoValidSuperblock`.
2. Обраний суперблок перевіряється далі, **без відкату** на інший:
   - `arena_used` < 0 або > довжини образу → `ArenaUsedOutside` (це **обрізаний** образ, а не
     привід читати попереднє покоління; тест `a_cut_one_cell_short_is_refused_not_read_as_the_previous_generation`);
   - `pt` < 0, або `pt` ≠ 0 і `pt + 20` ≥ довжини → `PartTabOutside`;
   - `pt` ≠ 0: довжина PartTab < 19 або об'єкт не вміщується → `PartTabBad{got: None}`;
     crc PartTab (§6) не збігається → `PartTabBad{got: Some}`;
   - корінь `r = cells[pt + 18]`: `r` < 0 або (`r` ≠ 0 і `r + 2` ≥ довжини) → `RootOutside`.
3. Відкат на інше покоління дозволено **лише** між суперблоками з поганим magic/crc15.

Rust-читачі `Store::pick`, `pick_in` (`View`) і `Store::begin` застосовують це правило; `begin`
повертає `StoreError::NoSuperblock` або `StoreError::Image(PickError)`. `Store::pick` — **окрема
коротка копія** правила (без імен відмов), бо її лінкує wasm-читач, чий байтовий храповик лише
спадає (виклик `pick_checked_in` коштував там +138 байт); `format/catalogue_tests.rs` на кожній
названій зіпсованій комірці перевіряє, що `Store::pick` = `pick_checked_in(..).ok()`.

## 4. PartTab (P = 1)

Об'єкт (§5) із 19 комірками payload (`PARTTAB_CELLS` = 16 + 3·P), разом із заголовком 21
(`PARTTAB_OBJ_CELLS`). Коміт з живого суперблока `sb` пише його в **хвіст сторінки іншого
суперблока** (тобто на сторінку нового суперблока): `pt = (512 − sb) + 16` (`PT_PAGE_OFFSET` = 16), тобто 528 для коміту з A і 16 для
коміту з B. Новий суперблок `512 − sb` називає його в комірці 3.

| Payload | Комірка відносно `pt` | Значення |
|---|---|---|
| h0 | `pt + 0` | `(digest_lo32 << 32) \| 19` |
| h1 | `pt + 1` | `(crc32(payload[0..19]) << 32) \| (gen mod 2³²)` |
| 0..15 | `pt + 2 .. pt + 17` | копія **попереднього** живого суперблока (того, з якого почався коміт), комірки 0..15 |
| 15 | `pt + 17` | перезаписано: crc32 над payload[0..19], обчислений, поки payload[15] ще тримав копію старої комірки 15 |
| 16 | `pt + 18` = `PT_ROOT` | `root_p`: абсолютний індекс кореня даних, 0 = немає |
| 17 | `pt + 19` = `PT_CURSOR` | `used_p`: курсор письменника = `arena_used` нового суперблока |
| 18 | `pt + 20` = `PT_GEN` | `gen_p` = генерація нового суперблока |

- `begin` бере курсор і генерацію **з PartTab**, а не з суперблока (як `st_begin`); при `pt` = 0 —
  з комірок 4 і 2 суперблока.
- `digest` PartTab: Rust **переносить** дайджест попереднього PartTab (0, якщо його не було — тобто
  в образі, створеному Rust, він 0 назавжди); bebop пише `st_digest("PartTab")`. Жоден читач
  дайджест PartTab не перевіряє.
- Внутрішній crc у payload[15] жоден читач не перевіряє; перевіряється crc у h1 (§6) — так само,
  як `st_check` у bebop `st_anc_ok`.

## 5. Об'єкт

```
h0 = (layout_digest & 0xFFFF_FFFF) << 32 | len        len = кількість комірок payload, ≤ 2³²−1
h1 = (crc32(payload) << 32) | (generation & 0xFFFF_FFFF)
payload[0..len]
```

- Об'єкти лежать в арені від `ARENA` = 1024 впритул, у порядку алокації; наступний коміт
  починає з курсора (`used_p`).
- `len` — **заява**: читач МУСИТЬ обмежити її образом (`obj_cells`); об'єкт, що не вміщується,
  має crc-провал `got: None`, а не алокацію.
- **`ref`**: payload-комірка зі **знаковим зміщенням у комірках відносно першої комірки
  заголовка об'єкта, що її містить**: `target = this_obj + off`; 0 = null. Ціль МУСИТЬ мати
  обидві комірки заголовка в образі, інакше це null (`follow`); додавання — з перевіркою переповнення.
- Генерація в h1 — лише нижні 32 біти (`MAX_GENERATION`, §10).

## 6. CRC

- zlib CRC-32 (поліном 0xEDB88320, init `0xFFFFFFFF`, final xor `0xFFFFFFFF`) над **сирими LE
  байтами комірок** — `zlib.crc32(struct.pack('<%dq' % n, cells))`. Rust: `crc.rs` (табличний,
  байт-у-байт рівний побайтовому); bebop: `crc32x`.
- Суперблок: crc над комірками 0..14 → комірка 15.
- Об'єкт: crc над `len` комірками payload → старші 32 біти h1 (`seal`).
- Якір: crc над комірками `[mark, arena_used)` (§7).

## 7. Якір `anc` (комірка 9)

```
anc = (mark << 32) | crc32(cells[mark .. cursor))
```

`mark` — курсор на початку коміту, `cursor` — після останнього об'єкта коміту (= новий `arena_used`).
Діапазон охоплює **лише арену** — PartTab має власний crc.

- Пишуть: bebop `st_commit_x` (з DG5) і **Rust `stage_commit` з W-ES-P0** (рішення оператора
  Q5, 2026-10-27). Версія контейнера лишається 2.
- `mark` читається **логічним** зсувом (`anc as u64 >> 32`; у bebop `>>` логічний).
- Поле `mark` — 32 біти: коміт, що починається за `MAX_ANCHOR_MARK`, пише `anc` = 0.
- Читач МУСИТЬ приймати і 0, і ≠ 0. Перевірка (`format::anchor_in`, правило `st_anc_ok`):
  `1024 ≤ mark ≤ arena_used` і crc діапазону = нижні 32 біти `anc` → `Holds`; інакше `Torn`.
  `anc` = 0 → `Absent`: доказ — лише обхід арени (bebop `st_reopen_verify`: обмежений обхід від
  `arena_used` іншого валідного суперблока).
- `pick` якір **не** перевіряє (це перевірка повторного відкриття, а не вибору); Rust-читач
  сьогодні не відкочується за якорем — відновлення є фазою P2.
- Якір лежить усередині crc суперблока: зміна лише комірки 9 робить суперблок невалідним.

## 8. Протокол коміту

**Rust → файл** (`Store::commit`): `stage_commit` у пам'яті (PartTab у сторінку іншого
суперблока, потім інший суперблок з `anc`), далі

1. `pwrite(cells[mark..cursor))` → `fdatasync`;
2. `pwrite(PartTab, 21 комірка)` → `fdatasync`;
3. `pwrite(суперблок, 16 комірок)` → `fdatasync` — **точка коміту**.

Падіння між будь-якими двома кроками лишає генерацію k читабельною: нічого, що називає
старий суперблок, не перезаписано (арена лише дописується, PartTab нового покоління лежить
на іншій сторінці, ніж PartTab старого).

**Rust → без ФС** (`commit_bytes`): лише стадіює; атомарність дає той, хто зберігає байти (у
dowiz — DO, атомарний `put` змінених чанків + мета, `workers/api/src/hubdo/atomic.rs`).

**bebop → mmap** (`st_commit_sync`): `msync([mark, cursor))` → запис PartTab+суперблока →
`msync(сторінки 0–1)`; два бар'єри.

**Створення** (`Store::create`): суперблок A (gen 0, `pt` 0, `used` 1024, ємність
`size/8 − 1024`, crc), решта нулі; файл записується, `fsync` файла, `fsync` каталогу (з W-ES-P0).
Нижче `MIN_BYTES` — відмова.

## 9. Розкладки над контейнером

Корінь розкладки — `cells[pt + 18]`. Версія розкладки — поле в її корені; невідома версія —
**відмова**, не здогад.

### 9.1 KV (`kv.rs`, `kv/delta.rs`)

Дайджести: корінь `DIGEST_KV_ROOT`, масиви й записи `DIGEST_ARR_I64` (пінені, бо sha256
лишається на боці bebop). Ключі в базі **відсортовані** за сирими байтами, строго за зростанням.

- **v1** — корінь 5 комірок `{n, ref KIDX, ref KBLOB, ref VIDX, ref VBLOB}`; KIDX/VIDX — `2n`
  комірок `(offset, len)` (мінімум 1); KBLOB/VBLOB — **один байт на комірку** (мінімум 1 комірка).
- **v2** — корінь 6 комірок, `+ VERSION = 2`; offset/len у **байтах**; блоби пакують 8 байт у
  комірку LE, `max(1, ceil(bytes/8))` комірок, хвіст нульовий. Версія: корінь ≥ 6 комірок і
  `payload[5] > 0` → це версія; інакше v1.
- **v3** — корінь 8 комірок `{.. v2 .., VERSION = 3, ref DELTA, D}`: база v2 + ланцюжок
  записів, найновіший перший; `D` — **заява** про довжину ланцюжка.
  Запис (дайджест `arr i64`): `{ref NEXT (старіший, 0 = немає), OP (1 put, 2 remove), KLEN, VLEN,
  ключ ceil(KLEN/8) комірок, значення ceil(VLEN/8) комірок}`; довжина МУСИТЬ дорівнювати рівно
  `4 + ceil(KLEN/8) + ceil(VLEN/8)`; remove має `VLEN = 0`. Обхід, що дає не рівно `D` записів,
  або записи, що разом займають більше комірок, ніж образ, — відмова (це ж закінчує петлю).
- **Читання** = база, потім записи від найстарішого: put вставляє/перезаписує, remove видаляє.
  Перевірка: crc кореня, чотирьох масивів і кожного запису (`Kv::load_checked`, `KvIn::open`).
- **Fold** (`snapshot_root_u64`): FNV-1a 64 над `len_le64 ‖ key ‖ len_le64 ‖ value` по записах у
  порядку ключів — над байтами, тож v1/v2/v3 тих самих записів дають один корінь.
- **Компакція** пише v2 у свіжий образ (подвоєння від 16 KiB до стелі), `to_bytes_trimmed`.
  Письменник дельт компактує, коли ланцюжок перевищив би `MAX_DELTAS`, коли
  `superseded · DEAD_DIV > live`, коли база v1 або арена повна.

### 9.2 EvLog (`evlog.rs`)

v1 корінь 7 комірок `{n, ref LAST, has_tip, tip0..3}`, v2 — 8 комірок `+ VERSION`. Запис v2:
`{actor_seq, payload_len (байти), ref prev, id0..3, prev_id0..3, flags, [actor_pubkey 4], payload
packed}`; v1 — 15 комірок заголовка й один байт на комірку. Повний опис — модульний коментар
`evlog.rs:12-45`; правило карантину — `verify.rs` `chain_scan`.

### 9.3 PROJTAB / PROJ / OUT (`proj.rs`)

Із суперблока, комірка 5: `PROJTAB [m, (key64, ref PROJ, kind) × m]`, `PROJ` 9 комірок,
`OUT [value, count]`; `input_gen` порівнюється з нижніми 32 бітами h1 кореня входу (ліміт §10).
Опис — `proj.rs:1-21`. Це розкладка DAG-рантайму dowiz, не частина публічної бібліотеки (Q6).

## 10. Константи й ліміти

Кожен рядок нижче виводить тест (T-ES-08); ліміт відмовляє **на межі + 1** і приймає на межі
(`format/tests.rs`).

|---|---|---|
| `MAGIC` | 3554557610294396226 | «BEBOPST1» LE |
| `FORMAT_VERSION` | 2 | комірка 1 |
| `SB_A` | 0 | суперблок A |
| `SB_B` | 512 | суперблок B = байт 4096 |
| `SB_CELLS` | 16 | комірок у суперблоці |

| `PARTTAB_OBJ_CELLS` | 21 | з заголовком |

| `PT_ROOT` | 18 | `pt + 18` = корінь |
| `PT_CURSOR` | 19 | `pt + 19` = курсор |

довжиною, `check_entry`). Розмір образу понад 512 MiB через файл — **не вимірювано**.

## 11. Розбіжності (знайдено R-EMBED-STORE §1.4, закрито/записано W-ES-P0)

Інші розбіжності, помічені під час заморозки:

- **oracle.py** не перевіряє crc PartTab (і якір); він погоджується з Rust на всіх фікстурах,
  бо фікстурні PartTab-и цілі. Образ із зіпсованим PartTab Rust і wasm-читач (він іде через
  `Store::pick`) тепер відмовляють, а oracle.py прочитав би — до P4 (конформація `torn-pt.store`)
  це розбіжність читачів. Якір не перевіряє жоден читач, крім `format::anchor_in`.

- **`Superblock.root`** у Rust API — це комірка 3, тобто індекс **PartTab**, а не корінь даних
  (історична назва; корінь — `Store::root()`).
