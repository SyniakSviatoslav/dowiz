# SPEC-PCD — the published price root and the receipt certificate (v1)

Date: 2026-10-27 (written 2026-10-28 by lane LV-PCD-C). Source: `docs/research/R-BEBOP-LEVERS-2026-10-27.md` §4.4, §7.3 (AC-LV-PCD-01..03).
Shape after `bebop-lang/docs/CERTIFICATE-FORMAT.md` §1-2: **this text is normative; every binary is derived from it**, the checker is a loop with no search, and every malformed shape has a named red example.

## 1. The tree (RFC 9162 §2.1)

- `H = SHA-256`. `leaf(d) = H(0x00 ‖ d)`, `node(l, r) = H(0x01 ‖ l ‖ r)` — leaves and nodes are domain-separated, so a node hash is never accepted as a leaf (`bebop-lang/formal/Bebop/Merkle.lean`, `verify_binding_leaf`); the pair hash is injective on `(l, r)` up to SHA-256 collisions (`hinj`, a hypothesis in the theorem, never an axiom).
- `MTH([]) = H("")`; `MTH([h]) = h`; for `n >= 2`, `k` = the largest power of two `< n`, `MTH(D) = node(MTH(D[0:k]), MTH(D[k:n]))`. No padding.
- The path of leaf `m` is BOTTOM-UP, siblings only (RFC 9162 §2.1.3.1). The side of each sibling is a function of `(m, n)` (§2.1.3.2), so a path carries no side bits. `Merkle.lean`'s path is top-down with explicit sides: the Rust path zipped with its sides, reversed (`crates/bebop-store/src/merkle/tests.rs lean_twin_verify_path_on_five_leaves`).

## 2. The price leaves

- One leaf per product of the published menu fragment (`categories[].products[]` with a string `id` and an integer `price`): `d = field(utf8 id) ‖ field(price as i64 LE)`, `field(b) = u64 LE len(b) ‖ b` (the node-key field, `crates/bebop-store/src/nodekey.rs`).
- Price = integer minor units of the venue currency. **Base price only**: modifier surcharges are not leaves in v1.
- Leaves in id BYTE order. A dish listed in two categories is one leaf. One id with two prices: **no root** (refused, never resolved).

## 3. The certificate (one receipt line)

```
cert := 'V' ‖ field(id ≤ 256 B) ‖ field(price i64) ‖ field(index u64) ‖ field(n u64) ‖ field(root, 32 B) ‖ field(path, 32·k B, k ≤ 64)
```
Strict: every number field is 8 bytes, the root 32, the path a multiple of 32, nothing after the last field.
Check: `leaf = H(0x00 ‖ cert[1 .. end of the price field])`, climb by RFC 9162 §2.1.3.2, compare with `root`.

| status | meaning | named red example (`crates/bebop-wasm/fixtures/verify/`) |
|---|---|---|
| 0 | the path climbs to the named root | `good.cert` |
| 50 | malformed: does not parse, `index >= n`, a path too short or too long for `(index, n)` | `short.cert` (one byte cut) |
| 51 | mismatch: the path climbs elsewhere (the climbed root is reported) | `path.cert` (byte 0 of the first sibling flipped), `price.cert` (price + 1) |

Readers (`crates/bebop-wasm/verify.sh` holds all four to `fixtures/verify.expected`): `bebop_store::merkle` (native), `crates/bebop-wasm/src/verify.rs` (wasm32, the browser's `verify.wasm`), `crates/bebop-wasm/oracle_verify.py`, `bebop-lang/selfhost/prelude/merkle.bp`. Producers: `bebop_store::merkle::Cert::of`, `workers/api/public/store/verify.js certFor` (byte-identical to the fixture, `verify.test.mjs`).

Size: the path is 32 B a level. 165 dishes = 8 levels = **256 B**; a 10⁴-leaf tree is 14 levels = 448 B (the research's "≤ 256 B at n ≤ 10⁴" is not reachable with full SHA-256 siblings; the bound that holds is n ≤ 256). A whole certificate for a 165-dish menu is ~366 B, ~490 base64url characters in the QR link.

## 4. The manifest and the signature

`v/<slug>/manifest.json` (`workers/api/src/hubdo/publish.rs`, `publish/root.rs`) gains:
- `root` — hex MTH over §2's leaves of the published fragment; `n` — the leaf count;
- `sig` — the key of a content-addressed object `{alg: "ML-DSA-65", pk, sig, msg}` (base64 / hex), or `null` when the venue holds no key ("unsigned" is said, not implied);
- `pk_id` — hex of the first 8 bytes of `SHA-256(pk)`, only when signed.

Signed message (`bebop_store::merkle::signed_message` = `publish/root.rs signed_message`):
`'R' ‖ field("dowiz-price-root-v1") ‖ field(slug) ‖ field(catalog generation i64) ‖ field(n u64) ‖ field(root)`,
signed with ML-DSA-65 `Sign_internal` (`crates/dowiz-core/src/pq/dsa.rs`, FIPS 204, ACVP-gated), deterministic (`rnd = 0^32`), key = `KeyGen(seed)` with the 32-byte seed in the `VENUE_SIGN_SK` Worker secret (64 hex). One platform key, created by the operator, never rotated (decision Q4). An unchanged message is never signed twice (the publish record keeps `signed`).

## 5. What v1 does NOT prove

- The browser does not check the ML-DSA signature (no ML-DSA in `verify.wasm`); `/store/verify.html` says so.
- A receipt is checked against the root it names; whether that root is the venue's CURRENT one needs the network (the page compares with the live manifest). Past roots are not archived yet (PROJ kind 5 ROOT, a later lane).
- Stock day-close witnesses and fiscal documents (AC-LV-PCD-04/05) are not in v1.
