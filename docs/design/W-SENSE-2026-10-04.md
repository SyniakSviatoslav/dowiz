# W-SENSE: taste, texture and aroma, per dish and per guest (2026-10-04)

Operator ask (2026-10-04): the taste profile, the AI analytics and the dynamic storefront need
extending; dish cards on the storefront AND in the menu show every defined taste axis and the
texture; AROMA is a third dimension beside taste and texture, and guests are profiled on it too.
Binding rulings of the same day: personalisation is automatic (legitimate interest, no checkbox),
the server profile is keyed to the phone the guest gives, the device profile is on by default,
one-tap objection, NO fingerprinting ever. Never a price, a discount, an eligibility or a refusal
from a profile (EU Omnibus 2019/2161, GDPR Art. 22).

## 1. The dish's sensory profile (data)

One optional object on the catalogue product, `sense`, integers only, closed vocabulary:

    "sense": { "v": 1,
               "taste":   { "sweet": 0..5, "sour", "salty", "bitter", "umami", "spicy" },
               "texture": { "crispy": 1..3, "crunchy", "tender", "creamy", "chewy", "soft", "juicy", "silky", "flaky" },
               "aroma":   { "smoky": 1..3, "citrus", "herbal", "floral", "nutty", "toasty", "marine",
                            "fermented", "fruity", "earthy", "buttery", "spice-warm" } }

* An ABSENT key is "not declared" and is never drawn. A taste axis at 0 IS a claim ("not spicy at
  all") and is drawn as an empty bar with the figure 0; a texture or aroma tag sent at 0 is removed
  (a tag is either there, at 1..3, or not). Anything outside the vocabulary or the range is a 400
  by name; the vocabulary ids are stable (`dowiz_hub::sense`), the words live in four languages.
* Validation is `crates/dowiz-hub/src/sense.rs` (hub tests). The owner's `POST /api/owner/products/:id`
  takes `sense` beside the old fields; any catalogue write moves `menuVersion` (as before).
* THE OLD FIELD. `taste` (five axes spicy/sweet/salty/sour/richness, levels 1..3) stays readable:
  a product with no `sense` reads its taste axes from `taste` at level x5/3 rounded (1->2, 2->3,
  3->5); `richness` has no axis in the new set and is not carried over. Writing `sense` clears the
  old `taste` so a dish never holds two answers.
* SUGGEST: `POST /api/owner/products/:id/sense/suggest` answers a DRAFT the owner reviews and saves
  with the ordinary save; it never writes. In this tree the draft is the deterministic lexicon
  (dish-name patterns of the common sushi menu = the starter defaults, and description/ingredient
  words in sq/en/uk/ru). The venue's own AI chain (W-AI, `services/engagement/ai`, merged in main
  after this tree's base) is handed back: `dowiz_hub::sense::from_model` is the pure validator
  that holds a model's answer to the vocabulary.

## 2. Cards and filters

* Storefront grid card: a compact six-bar strip (only the declared axes) + at most two chips;
  dish sheet: labelled bars with the figure as text (`aria` + visible "3/5"), texture chips,
  aroma chips. Owner menu row: the same compact strip. Nothing at all when nothing is declared.
* Filters (storefront): chips computed from what the menu actually declares ("spicy", "not
  spicy", "crispy", "creamy", "smoky", ...); AND across chips; pure predicate over data
  attributes written on the card once, so it works offline from the cached menu.

## 3. The guest on the same axes

* Device (`store/taste.js`): the sense vector is folded from the dishes the guest ordered,
  re-ordered, opened and added (same weights and 60-day half-life as the tags), over the CURRENT
  menu. Ranking adds a cosine match of a dish's own sense vector against the guest's, so a dish
  never ordered is predicted from its axes; the strip says why ("because you often pick smoky +
  crispy").
* Server (`services/customers/taste*.rs`): `Profile.sense` (keys `t:sweet`, `x:crispy`,
  `a:smoky`, UNIT per portion x intensity share), faded like the tags; `taste_sync` may carry the
  device's `sense` map (closed keys, 0..1000).

## 4. Context

* Band (morning / midday / afternoon / evening / night) and weekday from the VENUE's clock; the
  weather at the VENUE from Open-Meteo (`/v1/forecast`, no key), venue coordinates only, never the
  guest's location; edge-cached one hour per venue; any failure = no weather, never an error.
* `GET /api/public/locations/:slug/context` -> `{contract, band, weekday, weather|null}`.
* Each order folds its bucket into the profile (`ctx` weights per bucket and a weekday x band
  count); the storefront ranks with the current bucket's weights.

## 5. Session mood (device only)

Four one-tap chips -- quick energy, cosy, light & healthy, treat -- each a fixed axis weighting
for THIS page session, held in memory, never stored, never sent (no-tracking rule 6).

## 6. Adaptation history

Monthly snapshot of the vector, on the device (`months`, last 13) and on the server
(`Profile.months`, last 12); shown to the guest ("your taste over the year") and on the owner's
guest card; forget / objection / export cover it because it lives inside the same record.

## 7. Owner analytics and offers

* Segment builder: sense key x strength x recency (not seen N+ days) x frequency (orders >= N) x
  band. Answers a count, a 6-month trend from the monthly snapshots, and a planning hint (the
  weekday x band where the segment orders most, and the dishes that carry the key).
* Offers: only through a channel where the guest gave marketing permission for THAT channel
  (consent fold, `PURPOSE_MARKETING`), labelled as a personalised offer (Omnibus 2019/2161), the
  price read from the catalogue's public price (the body has no price field), optionally a
  loyalty bonus on top. Never a raised or worse price, never a refusal; allergens and health are
  not keys of the vocabulary, so they cannot be targeted.

## 8. Device context

Feature detection of the wallets the browser offers (Apple Pay `canMakePayments`, Payment
Request) orders the pay buttons. Nothing is stored or sent; no-tracking stays green.
