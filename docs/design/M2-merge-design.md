# M2: дизайн злиття (рішення, не код)

**Статус 2026-11-01: збудовано як M2-min, не ширше; що змінилося проти цього дизайну, §13; межі, FORMAT §14.** Лейн W-MG-M2D, 2026-10-31. Дерево = main f1da4b6e + M3, M4, M5, M6b, MIG. Жодної збірки й жодного запуску: кожне твердження нижче прочитане в коді, цитата поруч. Що не прочитане, позначене UNVERIFIED. Коду не змінено.

Рамки: R-EMBED-STORE §12.2 (ціль), R-MAINGOAL-A §1.2, §2a, §7 рядок M2 (план), R-MAINGOAL-B §4 і §6 рядок 3 (сумнів), оператор: склеювання є єдиним контрактом commit/merge/sync, шлях читання й байти незмінні, склеювання виявляє і не вирішує.

## 0. Висновок

1. **Рекомендація: M2-min, 3 лейни, лише бібліотека.** Два DOC-файли з одного генезису зливаються без сервера в один файл, конфлікт названо, злиття підписане. Усе складне (зріз, чуже стирання, відкликання) є іменованою відмовою. Без дроту, без Worker, без планшета. Цього досить для демонстрації M7. Повний M2 (12–13 лейнів) вирішувати лише після інтерв'ю.
2. **Формат не змінюється.** MERGE є тілом запису, а не об'єктом: нуль нових розкладок, DOC лишається v5, усі читачі бачать його як звичайний запис (§2).
3. **План недооцінив M2 у двох місцях.** Рядок M2 каже «`Tail.base` стає фронтиром, S2 окремий випадок». У коді це не так: S2 перераховує id, тож підпис планшета не переживає адопцію (§1.2). І DOC існує лише над журналом замовлень, а склеювання лише над складом: вони ніде не зустрічаються (§1.1).
4. **Якщо злиття потрібне лише ресторанам, M2 майже зникає.** S2 уже робить це через хаб. Ціна чесності: слова «без сервера» в §12.2 і демонстрацію M7 тоді треба переформулювати (§9).
5. **Знайдено окремий дефект, не пов'язаний із попитом:** запис REVOKE ніхто не читає; `verify` вірить лише таблиці KEYS, яку ніхто не підписує (§5.3). Це варто закрити незалежно від рішення щодо M2.

## 1. Що є насправді

### 1.1 Два світи, що не перетинаються

| | DOC і печатки | Склеювання S0–S2 |
|---|---|---|
| Журнал | лише замовлення: `doc_seal/sealed.rs:58` `seal_hub` через `Hub::load` | лише склад: `glue.rs:188` `load` через `StockLog`, `wire.rs:148`, `merge.rs:88` |
| Актор | `actor_id = sha256(pk)`, `seq` на пристрій (`write.rs:114`) | `actor_pubkey = 0` (`stock/log.rs:174`), `actor_seq = EvLog::len` (`:177`) |
| Хто офлайн | ніхто: на планшеті журналу замовлень немає за правилом (`glue/orders.rs:5-9`) | планшет кухні, `bebop-wasm --features tablet` (`glue/tablet.rs:4`) |

Офлайн пише лише склад, а печатка є лише на замовленнях. Під `doc::verify` два планшети зі `stock/log.rs` були б одним актором 0 із колізіями `(actor, seq)`, тобто форками (`verify.rs:123,130`). Отже M2 потребує третьої речі: журнал складу під DOC, із `seq` на пристрій. `SealedHub` є зразком опт-ін обгортки (`doc_seal.rs:23-26` пояснює, чому не сам `Hub`).

### 1.2 S2 є rebase, а не об'єднанням ланцюгів

`merge.rs:1-4` каже «as written», і це правда про байти payload, не про id. Адопція пише через `write_payload` (`stock/adopt.rs:120-121`), а той бере `prev = EvLog::tip` (`stock/log.rs:166`). Id є `sha256(prev ‖ payload)`, тож кожен адоптований запис отримує **новий** id. `tablet::rebase` (`tablet.rs:88`) потім кладе планшет на tip хаба. Наслідки:

- печатка планшета над його tip не назве жодного запису у файлі хаба: `names_record` хибне (`verify.rs:204`);
- якір над записом планшета теж осиротіє (`anch.rs:263`);
- фронтир із однієї голови існує лише «на дроті»: рядок `(0, seq, tip)` не описує ланцюг пристрою.

**Виправлення плану (R7 і §1.3 п.2):** `Tail.base` не міняємо. Поруч стають другі двері з незмінними id. S2 лишається як є для старих планшетів і для варіанта «лише ресторани».

### 1.3 Що вже готове під злиття

- `seal::message` не містить зміщень у файлі: лише actor, seq, tip, claimed_ms, prev_tip (`seal.rs:14`). Печатку можна перенести дослівно.
- `Record.prev` є попереднім записом **пристрою**, `ref prev` у EV є попереднім **у файлі** (`lib.rs:28,30`, `stage_append_in`). Порядок у файлі нічого не підписує.
- `verify` рахує по пристроях (`verify.rs:131,148`), форки вже є лічильником (`:130`), `holds()` вимагає `forks == 0` (`:89`).
- Перенесення з перепризначенням `ref ADMIT_REC` і `ref PREV_SEAL` уже написане двічі (`copy.rs:1-8`, `cut.rs:10-15`).
- `delta::obstructions` приймає згортки хвостів і не знає про ланцюги (`delta.rs:170`): конфлікт складу виявляється без зміни.
- Закон «нічого не втрачено» доведений (`Sync.lean` `no_event_lost`, `len_law`).

## 2. Точна розкладка MERGE

Запис `KIND_DECL` (`b'D'`, `history.rs:30`) за nonce M0, у ланцюгу пристрою, що зливає, під однією печаткою, тіло через `Ids::body`. `SealedHub::events()` пропускає `KIND_DECL` за іменем (`sealed.rs:223`), тож згортки не міняються.

```text
MERGE  "ein-merge/1"
       ‖ n_ours LE8   ‖ (actor_id 32 ‖ seq LE8 ‖ tip 32) × n_ours      HEADS нашого файлу до злиття
       ‖ n_theirs LE8 ‖ (actor_id 32 ‖ seq LE8 ‖ tip 32) × n_theirs    HEADS чужого файлу
       ‖ state u8                 1 FastForward, 2 Commutes, 3 Obstructed (`glue::State`)
       ‖ seg_root 32              корінь найновішого спільного SEG, 0^32 якщо зрізу не було
       ‖ dup_declared LE8         0 у M2-min; §5.2
       ‖ held_n LE8               скільки чужих записів не злито; 0 у M2-min
       ‖ n_conf LE8 ‖ (len LE8 ‖ bytes) × n_conf     кожен конфлікт як `conflict_body` (`merge.rs:160`)
```

Рядки відсортовані за `actor_id`, як HEADS (`seal.rs:8`). Два пристрої дають ~330 Б тіла плюс печатка 429 комірок.

Відмінності від §1.2 плану, усі навмисні:

| План | Тут | Чому |
|---|---|---|
| `heads_before` один список | два списки | §4 плану (DA): MERGE містить обидва tip-и, підписант мав обидва хвости |
| `glue_state ∈ {.., Resolved}`, `resolved[...]` | лише `Obstructed` + конфлікти | склеювання виявляє; рішення людини є наступним окремим записом, як `desk::close` (`desk.rs:67`) |
| `ref` не вказано | рядки за id, без `ref` | id переживає `copy_bytes` і `cut_into`, зміщення ні |

**Чому конфлікти всередині, а не окремі нотатки, як у S2.** Кожен запис DOC має печатку 3,4 КБ. І §12.2 каже «конфлікт названо»: аудитор бачить це з файлу, з одного підпису.

**Що нового читає `verify`** (лише Rust, лише M2-min): лічильник `merges` і `merges_bad`. Рядок поганий, коли `(actor, seq, tip)` не знайдено в `ids_at` і `tip` не під зрізом (та сама логіка, що `under_cut`, `anch.rs:264`). `Report::holds` отримує `merges_bad == 0`. Python/mjs-читачі MERGE бачать як звичайний запис і чесно не судять його (вони так само не судять підпис, `00_head.py:57`); додати лічильник туди означає ріст ratchet `tools/verify/bytes.baseline` 125017, рішення main.

## 3. Як фронтири замінюють `Tail.base`

Фронтир = рядки HEADS без `ref SEAL`, тобто `Vec<(actor, seq, tip)>`. Це вже є в кожному файлі (`seal.rs:59`). Новий тип не потрібен для M2-min: **обмін іде цілими файлами**, `Doc::merge_bytes(ours: &mut Store, theirs: &Store, ..)`. Дріт лише в повному M2:

```rust
pub struct DocTail { seen: Vec<Row>, recs: Vec<Record>, seals: Vec<Seal>, keys: Vec<Key>, anch: Vec<Anchor> }
```

**Алгоритм спільного предка** (замість `ancestor`, `glue.rs:219`, що йде «в ногу за позицією»). Для кожного актора з об'єднання: `s = min(seq_ours, seq_theirs)`; id на `(actor, s)` мусять збігтися, інакше `Fork`. Хвіст = записи актора вище `s`. Новий актор: весь його ланцюг є хвостом, і `prev` його першого запису мусить бути відомим id. Це нова перевірка, якої `verify` не робить: `first_ok` без рядка фронтиру каже `true` не дивлячись на `prev` (`verify.rs:135-138`).

Вартість O(dA + dB + акторів), як сьогодні. Межа плану `measure_glue` ≤ 150 мкс не застосовна до M2-min: там ще є ML-DSA.

**Запис** одна транзакція, зразок `commit_bytes`: чужі записи старші вперед і за зростанням `seq` у межах пристрою (`chains` бере порядок файлу, `verify.rs:119-123`), дедуплікація **за id** обов'язкова, бо дві копії одного запису `ids_at` порахує форком (`verify.rs:123,130`); потім печатки з перепідв'язаним `ref PREV_SEAL`, KEY з перепідв'язаним `ref ADMIT_REC`, якорі (дедуплікація за `(kind, over, time_ms, proof)`), HEADS як поточковий максимум, MERGE останнім через свій seq. Відмова не пише нічого, як у S2.

**Збіжність.** A зливає B і пише M_a; B зливає A і пише M_b. Далі хвости складаються лише з MERGE: правило «хвіст лише з MERGE приймається без нового MERGE» гасить шторм. Той самий файл двічі = нуль записів (аналог `replay`, `merge.rs:72`). Стан однаковий у двох реплік: комутативні рухи за `merge_comm_perm`; некомутативні (перерахунок) є `Obstructed` і чекають людину.

**Сумісність S2.** Не чіпаємо `Tail`, `tablet.rs`, `merge.rs`, `desk.rs`, wire-JSON (`glue_turn.rs:40`). Це слабше за план («S2 як окремий випадок»), але дешевше і правдиво.

Згортка: записи `chains` у канонічному порядку дають `Vec<StockEvent>`, далі `TailDelta::of` і `delta::obstructions` як є (`wire.rs:187-189`). `StockLog` не торкаємо.

## 5. Кожен випадок: що означає злиття

### 5.1 Пристрій, чий ланцюг зрізано

SEG зберігає позиції у файлі (`seg.rs:18-21`) і корінь над id **у порядку файлу**, рядки фронтиру на пристрій. Об'єднати «SEG + живі записи під ним» неможливо: найстарший запис актора нижче рядка фронтиру стане `broken` (`verify.rs:135-138`), `cut` порахує двічі.

| Випадок | M2-min | Повний M2 |
|---|---|---|
| Той самий ланцюг SEG (корені рівні) | працює: це спільне минуле | те саме |
| A зрізав, B ні, B має всі записи діапазону в тому ж порядку | `DocError::CutOneSide{root}` | B перераховує `Ids::tree_root` над своїм префіксом; збіглось: B бере SEG, його старий файл є архівом |
| Порядок записів у B інший або чогось бракує | відмова | `CutUnplaceable`: потрібен архів A, злиття на незрізаних копіях, потім зріз наново |
| B відстав нижче фронтиру (`seq_B < f.seq`) | відмова | `ArchiveNeeded{actor, seq}`: tip B не можна зіставити без архіву |
| Різні SEG на двох сторонах | відмова | відмова: дві різні компакції, лише через архіви |

**Чого зріз коштує чесно:** форк нижче фронтиру без архіву не виявити. Фронтир каже лише `(seq, tip)`.

**Краще правило для повного M2:** не різати нижче склеєного фронтиру пристроїв, які ще не бачились. Це `cut_into` з нижньою межею; ціна в тому, що один загублений планшет зупиняє ротацію. Тому це рішення оператора (§11).

### 5.2 FORGOTTEN, який має лише одна сторона

Редакція лишає `id`/`prev` (`seg.rs:4`), тому **порівняння фронтирів її не бачить**. Запис A стер у спільному префіксі, id той самий, хвіст несе лише FORGOTTEN. FORGOTTEN несе `n` і `subject`, а не id (`seg.rs:36`). Без додаткового кроку B лишає PII, а його `redacted != declared` і `holds()` хибне (`verify.rs:89`).

Правила повного M2:

1. **Стирання домінує.** Той самий id: надгробок перемагає, відкритий текст не повертається ніколи.
2. Хвіст несе список `redacted_ids`. Він не підписаний, але чинний лише за ефективного FORGOTTEN (`declare.rs:31-35`), і його довжина звіряється з `n`. Авторитет той самий, що сьогодні: допущений ключ може стирати.
3. Застосування є **перебудовою** `Doc::redact_into` (`copy.rs:47`), не дописуванням: bump-арена зберегла б відкритий текст у старих байтах.
4. Обидві сторони стерли одного суб'єкта: `declared` підсумує двічі (`verify.rs:281`, `60_count.py:30`), надгробків менше, закон 9 падає. Звідси `dup_declared` у MERGE, підписане злиттям. Це зміна лічильника у **трьох** реалізаціях (Rust, py, mjs).

M2-min: будь-яка асиметрія множини FORGOTTEN або надгробків є `DocError::ForgetOneSide`. Для складу це не трапляється: приватних ключів там немає за правилом (`wire.rs:17-22`).

**Важливе для юриста:** злиття є каналом стирання. Поки файл B не зустрів A, PII у B живе. Це випливає з самої моделі офлайн-копій.

### 5.3 Відкликаний ключ на тому боці

Файл A: REVOKE X після k. Файл B: X дописав і запечатав до m > k.

- Імпорт як є робить печатки k+1..m поганими (`keys.rs:59`, `verify.rs:208`), і **весь** файл перестає `holds()`. Один відкликаний планшет не має вбивати доказ файлу.
- `after_seq` обирає той, хто відкликає, бо годинникам не вірять. Записи вище k можуть бути злодія або чесної зміни. Це питання до людини.

Повний M2: записи вище k стають `held`, дослівно в тілі нотатки рішення (зразок S2, `merge.rs:121-122`), `held_n` у MERGE, закон `sent == merged + held` лишається. KEY об'єднується як `min` ненульових `revoked_at`. ADMIT від X вище k тягне за собою весь ланцюг допущеного: `admit_more` його не допустить (`verify.rs:235-237`), він теж `held`. Два ключі відкликали один одного: `DocError::MutualRevoke`, Keyhive це називає нерозв'язаним (R-MAINGOAL-A §2e).

M2-min: `DocError::RevokedTail{actor, after_seq}`.

**ДЕФЕКТ НЕЗАЛЕЖНО ВІД M2.** `verify.rs:32-34` каже, що `revoked_at` лише звужує. Але `parse_revoke` немає ніде в дереві (є лише `revoke_body`, `keys.rs:94`), чинність читається лише з таблиці (`keys.rs:59`), а KEY ніхто не підписує. Власник вкраденого ключа, що має файл, обнуляє `revoked_at`, і відкликання зникає мовчки: запис REVOKE лежить у ланцюгу, його ніхто не згортає. До того ж зріз захищає ADMIT (`cut.rs:105-109`), а REVOKE ні. Python і mjs `revoked_at` не читають зовсім (нуль влучань у `tools/verify`), що узгоджено з їхнім `checked=0`. Виправлення: згорнути ефективні REVOKE у `verify` і додати `CutsRevoke` у `cut.rs`. Це ~1 лейн, не залежить від рішення щодо злиття. RED-доказу ще немає: це прочитано, не запущено.

### 5.4 ANCH над записом, якого інша сторона не має

| Випадок | Результат |
|---|---|
| Запис приходить у хвості | ANCH іде за ним, `names_record` істинне (`anch.rs:263`), час зберігається, бо id не змінився. Це головний виграш перед S2-rebase |
| Запис у `held` | якір теж `held`, інакше `Bad("names no record")` (`anch.rs:267-268`) |
| Запис пішов під спільний SEG | `Unchecked`, «місце в архіві» (`anch.rs:270-274`), як сьогодні |
| Якір над MERGE | **рекомендований:** id MERGE охоплює обидва фронтири, один якір фіксує час обох гілок |

ANCH не підписаний, тому переносити його безпечно: він нічого не стверджує, доки адаптер не перевірить. Запис не вибирає гілку (урок Ceramic, §2a).

### 5.5 Правило sha256/legacy «вперед один раз»

- `verify` застосовує його **на пристрій** (`verify.rs:139-163`), `moved` стартує зі `scheme` рядка фронтиру (`:145`). Злиття не ламає, якщо порядок пристрою збережено.
- `chain.rs:walk_check` застосовує його **до всього файлу** (`chain.rs:136-142`). `SealedHub::chain_check` кличе саме його (`sealed.rs:212-215`). Файл, де старий пристрій із legacy-записами дописався після sha256-запису іншого, вона назве зламаним, тоді як `verify` назве legacy. Перед M2 `walk_check` має групувати по актору, або `SealedHub::chain_check` треба прибрати на користь `doc::verify`.
- У хвості вище спільного предка legacy заборонено: `DocError::LegacyTail`. Нові ланцюги DOC завжди sha256 (`sealed.rs:179-182`). Старі планшети FNV лишаються на S2 (`wire.rs:34`).
- Предок на FNV-id не є доказом: FNV не стійка до підробки (`chain.rs:19-21`, R1 плану). Якщо спільний префікс legacy, звіт каже `inherited_prefix: n`, як §1.3 п.1 плану, а не «доведено».

### 5.6 Ще три пастки, яких немає в картці

- **Чужий генезис.** KEY без `ADMIT_REC` під `Trust::Genesis` допускається без доказу (`verify.rs:264`). Перенесений із чужого файлу, він стає новим коренем довіри. Правило: множини генезис-ключів рівні, інакше `DocError::ForeignRoot`.
- **Той самий актор, різний KEY.** `pk`, `alg`, `valid_from` мусять збігатися, інакше `DocError::KeyClash`.
- **Відновлення з резервної копії.** Планшет, відновлений зі старої копії, чесно продовжить той самий `seq`: це форк без зловмисника. План обіцяє `fork_id` у наступній печатці, але в `seal::message` його немає (`seal.rs:14`), тому це вже була б SEAL v2. M2 дає лише відмову. Правило експлуатації: відновлений пристрій отримує новий ключ.

## 6. Відмови

Нові варіанти `DocError` (стиль `doc.rs:92`, кожен названо): `Fork{actor, seq, ours, theirs}`, `ForeignRoot`, `KeyClash(actor)`, `CutOneSide{root}`, `ForgetOneSide`, `RevokedTail{actor, after_seq}`, `LegacyTail{actor, seq}`, `Carries("TREE"|"SPEC")` (уже є: дерево є похідним, SPEC лише в архівах). Обидва файли спершу проходять `verify(..).holds()`, інакше нема чого зливати. Відмова не пише нічого.

## 9. Якщо інтерв'ю скажуть «лише ресторани»

Ресторан має хаб: один письменник на венуї, планшети офлайн і повертаються до нього. S2 це вже робить разом із людським екраном (`desk.rs`, `tablet.js`).

| Що зникає | Чому можна |
|---|---|
| ML-DSA на планшеті, ключі пристроїв, допуск | ідентичність дає зміна на хабі; 3 лейни геть, K2 не потрібен |
| `DocTail`, файловий обмін, збіжність реплік | один письменник, rebase |
| Зріз | у складу немає ротації: `rotate.rs` працює над `Hub`; у `stock/` влучань немає (UNVERIFIED для майбутнього) |
| FORGOTTEN | у складу немає особистих даних: `Why::Tracking` (`wire.rs:17-22`) |
| Відкликання | немає ключів |
| Форк | rebase; `Why::NoCommonAncestor` дає 409 і чистий старт (`glue_turn.rs:59`) |
| Lean-фронтир | один предок |

Лишається лише, за бажання: підписувати `glued`-нотатку хаба. Це 0–1 лейн.

**Ціна:** §12.2 «зливається без сервера» лишається невиконаним буквально. Планшети не підписують своїх записів: хаб може переписати їх непомітно, і довести протилежне нічим. Демонстрація M7 тоді показує лише бібліотеку. Це узгоджено з R-MAINGOAL-B (§4: злиття як бібліотечна фіча «найдорожче»; §6 ряд 3: «Після 2, лише на схемі dowiz»), але потребує вашого рішення змінити формулювання цілі.

## 12. Рішення лише оператора

- [ ] **Ціль.** «Зливається без сервера» лишається буквально чи стає «без постійного зв'язку з хабом»? Перше тримає M2-min і далі; друге майже скасовує M2 (§9).
- [ ] **Обсяг зараз.** M2-min (3 лейни) / чекати інтерв'ю / повний (12–13).
- [ ] **Дефект REVOKE.** Закрити зараз окремим лейном, не чекаючи M2? (Рекомендую так.)
- [ ] **K1.** Дозволити читання журналів складу на проді й qa-durres лише для підрахунку `glued`/`decide`? Нічого не змінює, але заборона деплою 10-31 не каже про читання.
- [ ] **Що показати на інтерв'ю.** Таблицю §7 як є? Якщо власник не може відповісти, що зробив би на рядках `Fork` і `RevokedTail`, сама семантика неправильна.
- [ ] **Підпис на планшеті.** Кожен планшет матиме власний ключ (довіра не залежить від хаба, ціна 3 лейни і байти) чи хаб свідчить за нього (дешево, але хаб може переписати)?
- [ ] **Частота печаток.** На кожен рух чи одна на синхронізацію? Друге дешевше, але проміжні записи тоді доводяться лише ланцюгом.
- [ ] **Записи після відкликання** (тільки повний M2). `held` до рішення людини (рекомендую) чи відкинути одразу? Викинуті записи чесної зміни це втрата; враховані записи злодія теж.
- [ ] **Зріз проти відсталого планшета** (тільки повний M2). Не різати нижче фронтиру (один загублений планшет зупиняє ротацію) чи різати за строком і вимагати архів?
- [ ] **Відновлення з копії.** Правило «відновлений пристрій отримує новий ключ» прийнятне? Альтернатива `fork_id` вимагає SEAL v2.
- [ ] **Стирання як канал** (тільки повний M2). Потрібна думка юриста: скільки часу офлайн-копія може тримати стерті дані? Це межа тривалості офлайну.
- [ ] **Ratchet.** Дозвіл main на ріст `tools/verify/bytes.baseline`, якщо лічильник `merges` піде в py і mjs? Без нього сторонній аудитор бачить MERGE, але не судить його.

## 13. Дельта M2-min (лейн W-MG-M2, 2026-10-31)

Рішення §12 за замовчуванням main: ціль буквальна; M2-min; одна печатка на синхронізацію; кожен пристрій свій ключ; відновлений пристрій бере новий ключ; планшет і Worker не чіпаємо. Що в коді інакше, ніж вище:

| Де | Тут було | Стало | Чому |
|---|---|---|---|
| §2 `state` | FastForward пишеться | не пишеться | одна історія не потребує MERGE; значення 1 розбирається, але MERGE при перемотуванні немає |
| §2 `merges_bad` | рядок поганий, коли його немає в `ids_at` | також тіло з позначкою, що не розбирається | непрочитаний MERGE не сміє читатися як відсутній |
| §2 читачі | Python/mjs не судять MERGE | судять, `merges` і `merges_bad` у всіх трьох, ABI 20 комірок, дописано в кінець | рішення main. Читач wasm, виміряно: без M2 133367, лише дві комірки 134029, з обходом MERGE 135548, із правками W-MG-LEAN 135753 Б проти ratchet 134195 |
| §3 `Doc::merge_bytes(ours: &mut Store, ..)` | у свій файл | `Doc::merge_into(ours, theirs, fresh, ..)` | перебудова, як `cut_into`; відмова не торкається файлу |
| §3 предок | `min(seq)` | префікс по актору, запис за записом | покриває й актора без ключа (до печатки), де seq не щільний |
| §3 хвіст лише з MERGE | лише «theirs» | MERGE потрібен, коли ОБИДВА хвости мають щось, крім MERGE | так гасне і перемотування, і шторм |
| §4 `SealedStock` | окремий тип | рід запису `KIND_STOCK` у `SealedHub`, `sync_stock` | мінімальний місток; `commit_many_bytes` одразу, бо одна печатка на синхронізацію є рішенням main |
| §5.5 `walk_check` | групувати по актору | не змінено | `SealedHub::chain_check` на об'єднанні лишається неправдивим, зведення його не кличе; судить `doc::verify` |
| §6 | немає | `NotWhole{ours}`, `UnionNotWhole`, `SealFork` | обидва файли і об'єднання проходять `verify`; `theirs` під НАШИМИ коренями, не своїми; печатки не губляться |

**Нове проти дизайну: повторне виведення конфліктів.** Рядки MERGE фіксують обидві сторони, тож `SealedHub::merge_lines` згортає ті самі дві сторони і порівнює з підписаним списком. Власник ключа, що приховав конфлікт, читається як `recheck=DIFFERS`, `doc_verify` дає rc 3. Це поза `verify`: бібліотека не знає семантики складу, тож `holds` на такому файлі істинне.

**Ще нове: зведений хвіст, викинутий разом із печатками.** Сам по собі це коротший правдивий файл (`k3_union`). Поки MERGE лишається у файлі, його рядок називає діру: `merges_bad`.

**Межа.** Об'єднання без MERGE тримається, тож власник файлу може зняти MERGE разом із печаткою; лишається коротший правдивий файл (`settle.rs`, ROLLBACK). Один файл цього не знає; зведення з копією, де MERGE є, повертає його.

Lean-фронтир із §8 (`Sync.lean`) у цьому лейні не зроблено: це наступний рядок.
