## 0. The answer in ten lines

1. **bebop's DATA is already a DAG; its COMPUTE is not.** Content-chained log, content-addressed modules
   (`cas://`), hash-checked folds that four readers reproduce — all in the tree (§1.1). But the compile key is
   the whole program, every log reader walks the whole chain, the KV image is rewritten whole, and the one
   general dataflow evaluator ever built here lost 41x on dense work (§1.2).
2. **A one-line edit costs the full self-compile: 14.4-14.7 s on this box today vs a 156-174 ms `.becache`
   hit** (MEASURED, artifact identity `d1dedc62 == compile(bebop.bp) == gen3` verified first). The committed
   row says 1.5-1.7 s; the control shows the cores at 0.69-0.96 GHz of 2.4 and a compile cost that grows as
   **fn-count^1.85** (701 fns: 2,061 ms; one 104 KB fn: 130 ms) — quadratic name scans, not bytes (§2.2).
3. **Incremental compilation as a query DAG lands the one-line edit at ≈ 120-150 ms (EST on measured
   parts): ~100x today, ~12x against the committed row** — main's 5-50x confirmed and exceeded. The cold
   compile is unchanged (crc32x keys cost 0.3 ms). The cheaper row first: an O(1) name table alone is EST
   3-6x on the cold compile for ~50 lines (§2.2, §6 row 1).
4. **The store as projections: 254x at the hot-log size, 1,274x at 10x** (full refold 5.75 ms vs `fold_step`
   0.023 ms, MEASURED on bebop-store) — main's 10-1000x confirmed. The bigger surprise: the Rust reader's
   `from_bytes` copy is 31 ms, 5x the fold, and the KV catalogue image is 8x its payload (one byte per cell) (§4).
5. **Runtime DAG scheduling on three cores reaches 2.5-2.7x on independent work ≥ 40 ms per level, 1.0x on
   0.1 ms tasks, 0.85x on a pure chain, and is deterministic (fold identical at W=0..3 in all 40 runs)**
   (§3.3, a `.bp` ready-set scheduler probe). It buys nothing on a venue's request path (every kernel is
   microseconds) and pays on the compiler's 348 fn nodes and the store's whole-image work.
6. **Prices/stock as tensors on SIMD: refuted at every scale.** The sparse scalar mask is 8x faster than the
   best simd128 dense form at 165/120/70 (1,089 vs 9,749 ns) and 580x at 100x; prices and portions gain 0 %
   (no integer divide / i64 mulhi in v128). All kernels together are 8.3 µs — 0.08 % of the 10 ms wall (§12.3).
7. **The codec is where the time is: JSON parse 6.33 ms vs block decode 2.4 µs (2,600x), a placement's
   `bom_of` parses 41 µs vs 5 × 82 ns.** A columnar block that is the wire and memory format wins by three
   orders of magnitude at the edges and is 52x smaller; SHA-256 of the block is 30 µs vs 1.54 ms of the JSON (§13.2).
8. **Datalog is cheap and belongs on the dirty set: 82 ns per stock event, 40x under naive re-derivation at
   1x and 2,260x at 100x** (§12.3); the design (semi-naive, stratified negation refused inside cycles, rules
   as data over declared edges, Lean once per stratum) is §12.1.
9. **CAS for everything: yes for code, media, catalogue versions, archives, projection outputs (mostly what
   exists: content ids, content-addressed media, changed-chunk writes; DO limit is 2 MB SQLite-backed, chunks
   96 KiB); the live log is a chain, and personal data forces the one exception — crypto-shredding for new
   logs, declared redaction for history, GC never as the deletion mechanism** (§11.1).
10. **The one-jump plan (§8)** replaces the driver's memo, the store's read path and the worker pool in ONE
    commit across three lanes, shown correct against the pre-jump commit's frozen binaries (360 programs
    byte-identical), the fixpoint, the four-reader fold, `dagfull` (warm == cold, per node) and the Lean
    confluence theorem. Ranked rows and the five "do not" rows with the numbers that refute them: §6.

## 2. Incremental compilation as a query DAG

### 2.1 Control: artifact identity and what a compile costs today (MEASURED, slot `bdag`, cores 4-6, 04:31)

`bebop.bin d1dedc62 == compile(bebop.bp) d1dedc62 == gen3 d1dedc62` — the promoted compiler IS the source's
compiler and its own fixpoint (206,880 B). `bebop.bp`: 348 top-level fns, 9,122 lines, 457,622 bytes.

| Path | Wall (3 runs) | Note |
|---|---|---|
| cold self-compile (`.becache` absent) | **14,496 / 14,724 / 14,404 ms** | rc=0; the ROADMAP Measured row says 1.5-1.7 s (2026-09-06, 6,909-line source). The 9x gap is re-measured under a control in §2.2 before it is believed |
| warm `.becache` hit (compiler bytes ‖ expanded source ‖ output identical) | **174 / 159 / 156 ms** | the hit is the process floor + streaming 669,351 B of cache record; no emission |
| one-line edit (a comment inserted at line 3; cache present, stale) | **14,571 ms**, then 136 / 141 ms | the first compile is a MISS = a full compile; it rewrites the record, so the two repeats hit. `edit.bin` = `d1dedc62`: a comment does not change the output, yet the whole program was re-emitted |
| `check` (no output, no cache) | 14,475 / 14,693 / 14,702 ms | = the compile: planning + emission both run; nothing is memoised at fn level |
| gen3 (gen2 compiling the source) | 14,070 ms | same digest |

So the answer to "what does a one-line edit cost today" is: **the full compile, ~14.5 s on this box now
(1.5-1.7 s by the committed row)**, against a **~160 ms** hit when nothing changed. The memo key is the whole
program; the ratio miss/hit is 90x and nothing between the two exists.

### 2.2 Control for the 14.5 s, and the shape of the cost (MEASURED, slot `bdag` 04:58, throwaway tree copy)

Control: box idle (`loadavg 0.12`, 17 procs), pinned to ONE big core: **14,547 ms on core 4, 14,441 ms on
core 6** — the same as unpinned (§2.1), so it is not contention. The cores read **691-960 MHz of a 2,400 MHz
maximum** at both samples (`scaling_cur_freq`), i.e. this box is clocked at 0.3-0.4x today (boxguard / thermal
policy, AGENTS L19); that alone explains ≈ 2.5-3.5x of the 9x against the committed 1.5-1.7 s row. The rest is
the shape below. **Every RATIO in this section holds at any clock; the absolute 14.5 s is this box today.**

The cost is superlinear in the NUMBER OF FUNCTIONS, not in bytes (cold, pinned core 4, 2 runs each; floor ≈ 70 ms):

| fns | narrow body (1 call/fn) | wide body (8 calls/fn) | bytes narrow / wide |
|---|---|---|---|
| 101 | 83 / 89 ms | 116 / 124 ms | 11.4 / 15.1 KB |
| 201 | 123 / 123 | 242 / 256 | 22.9 / 30.2 KB |
| 401 | 261 / 232 | 750 / 719 | 46.3 / 61.7 KB |
| 701 | 676 / 478 | **2,063 / 2,061** | 81.4 / 109.0 KB |
| ONE fn, 3,000 `let`s | **136 / 126 ms** | — | 103.9 KB |

Above the floor the wide column grows 50 → 180 → 660 → 1,990 ms per fn-count doubling ≈ 3.6x, i.e. exponent
≈ **1.85 in fn count** (narrow: 16 → 53 → 176 → 507, the same exponent); a single 104 KB function of 3,000
statements compiles in 60 ms above the floor (0.6 µs/byte). So per-byte cost is small and the compile of
`bebop.bp` (348 fns, thousands of call sites) is dominated by a term that scales as fns × calls — the linear
scans over `fntab` per call site (`compile_fn_at` resets a "scan budget" `fntab[5600]` per fn, `bebop.bp:7252`,
which names such scans). HYPOTHESIS for the constant, MEASURED for the exponent.

Two consequences for the DAG design: (i) a per-fn memo cuts a one-line edit to one fn's share regardless of
the exponent (the memoised fns are not re-scanned), which is why §9's ~100x stands; (ii) an O(1) name table
(a hash over `fnames`) would cut the COLD compile by the same superlinearity — EST 3-6x at 348 fns — for ~50
lines and no DAG at all. It is the cheaper row and is listed first in §6 for exactly that reason.

### 2.3 Per-function cost, the fixed floor, and what a query DAG would make of it

Synthetic programs (N pairs of a 6-line fn + a 1-line helper, every fn calling the next), cold, 3 runs each
(MEASURED, slot `bdag`):

| fns | source bytes | wall ms (3 runs) |
|---|---|---|
| 51 | 5,811 | 73 / 79 / 83 |
| 101 | 11,636 | 102 / 81 / 86 |
| 201 | 23,286 | 119 / 114 / 99 |
| 401 | 47,087 | 229 / 228 / 232 |
| 801 | 94,687 | refused: `error[E104]: too many fns (cap 768)` — the fn table is a fixed 784-cell array (`bebop.bp:7495`) |

Floor ≈ 70 ms (seed + process; the becache gate measured 90-106 ms for a trivial program), slope ≈
**0.4-0.65 ms per small fn** (≈ 3.4 µs per source byte). `bebop.bp` at 457 KB and 348 fns costs 31 µs per byte —
**9x more per byte than the synthetic corpus**, i.e. the cost is not linear in size. §2.2's probe separates
"bigger functions" from "more functions" (a quadratic in fn count — linear name scans over `fntab` — is the
hypothesis; the `fntab[5600]` scan-budget reset at `compile_fn_at:7252` says such scans exist).

What a query DAG makes of a one-line edit (EST on the measured inputs):

- **Per-fn memo, position-independent code + link**: recompile 1 fn (≈ 41 ms at bebop.bp's measured
  average, or ≈ 5 ms if the superlinearity is removed first) + relink 206 KB (a copy + patching `bl`
  displacements: EST < 5 ms) + the floor 70 ms ⇒ **≈ 120-150 ms**, against 14.5 s today: **~100x**, and
  against the committed 1.6 s: **~12x**. The hit path (160 ms) is already at the floor, so a DAG cannot make
  the no-change case faster; it makes the one-change case cost what the no-change case costs.
- **Which passes are pure functions of their inputs**: `use_expand` (source → expanded source: pure, keyed by
  content), `collect_fns`/`collect_ctors` (expanded source → tables: pure), pass 1 per fn (fn source +
  tables → size, facts: pure per fn), prefix-sum layout (sizes → starts: pure, but every later start
  changes when one size changes), pass 2 per fn (fn source + tables + STARTS → words: pure per fn but
  DEPENDS ON EVERY EARLIER SIZE through `starts`), `scan_literals` (whole source → literal pool: pure, whole),
  `entry_stub`/export (pure). The only impure step is the `.becache`/output write. The one edge that makes
  the fn graph dense is `starts`: cutting it (relocations resolved at link) is what makes the memo per fn.

|---|---|---|---|
| `sha256_words` (software, `selfhost/prelude/sha256.bp`) | 4 MiB in 198-219 ms ⇒ **≈ 19-21 MB/s** | ≈ 17 µs | ≈ 27 ms |

## 3. Runtime dataflow: scheduling a DAG on the box's cores

### 3.1 The probe

`scratch/bdag/p6/dag.bp` (compiled by `bebop.bin d1dedc62` on the throwaway tree): a levelled DAG of N tasks
× L levels on W persistent `sys_clone` workers; tasks are claimed from a per-level atomic counter
(`sys_atomic_add`, LSE `ldaddal`, returns the old value — `bebop.bp:1985-1990`), a level ends when its done
counter reaches N (futex wait/wake, no polling), W = 0 runs the same schedule serially in the parent. Each
task is K iterations of an LCG in registers (compute-bound, no memory traffic, no allocation). The program
returns `(fold & 2^20-1) × 1e6 + wall ms`, so a wrong fold and the timing are both visible; every
configuration ran twice (AGENTS taxonomy row 7). The spawn function keeps 4 symbols across the clone.

### 3.2 Overhead: the barrier and the spawn (MEASURED, slot `bdag` 04:58)

| N × L × K | serial W=0 | W=1 | W=2 | W=3 | fold equal? |
|---|---|---|---|---|---|
| 8 × 4 × 200,000 (32 tasks, ≈ 6-9 ms of work) | 6 / 9 ms | 16 / 17 | 10 / 10 | 7 / 8 | yes (334352) |
| 8 × 4 × 20,000 (≈ 1 ms of work) | 1 / 1 | 4 / 4 | 3 / 3 | 9 / 9 | yes |
| 8 × 4 × 2,000 | 0 / 0 | 1 / 2 | 1 / 1 | 2 / 3 | yes |
| 64 × 8 × 2,000 (512 tiny tasks, 8 barriers) | 1 / 2 | 13 / 16 | 20 / 23 | 17 / 12 | yes (614656) |
| 3 × 4 × 200,000 (a chain-like DAG: 3 ready per level) | 3 / 4 | 5 / 6 | 5 / 5 | 3 / 2 | yes (708942) |

Read: with ≤ 9 ms of total work, W = 1-3 never beats serial — the 1-5 ms spawn+join floor (memory
`bebop-multicore-gives-nothing`, re-observed here: W=1 costs +2-10 ms over serial) plus **≈ 1.5-2.5 ms per
level barrier** (512 tiny tasks over 8 levels: 12-23 ms against 1-2 ms serial) eat everything. The fold was
identical at every W in every run: the ready-set scheduler is deterministic by construction (§7.4), and that
part of the design is confirmed. Speedup needs tasks large against the floor: §3.3.

### 3.3 Speedup at task sizes above the floor (MEASURED, slot `bdag` 05:19, cores 4-6 at 0.69-0.96 GHz)

| Shape | N × L × K | serial W=0 | W=1 | W=2 | W=3 | best speedup | fold equal? |
|---|---|---|---|---|---|---|---|
| levelled DAG, 8 ready per level | 8 × 4 × 5,000,000 (≈ 160 ms) | 159 / 159 ms | 161 / 164 | 81 / 83 | **62 / 63** | **2.55x** | yes (1006096) |
| narrow levels, 3 ready per level | 3 × 4 × 20,000,000 (≈ 240 ms) | 237 / 243 | 243 / 232 | 180 / 164 | **85 / 89** | **2.7x** | yes (500814) |
| many small tasks, 8 barriers | 64 × 8 × 100,000 (≈ 50 ms, 0.1 ms/task) | 50 / 58 | 142 / 152 | 65 / 75 | 46 / 60 | **1.0x** | yes (704768) |
| fully independent, one level | 24 × 1 × 2,000,000 (≈ 50 ms) | 49 / 50 | 74 / 64 | 32 / 32 | **18 / 21** | **2.5x** | yes (1013036) |
| a pure chain, one ready per level | 1 × 24 × 2,000,000 (≈ 50 ms) | 48 / 51 | 62 / 71 | 46 / 59 | 58 / 60 | **0.85x** | yes (1013036) |

Read against main's EST and the known facts:

- **Independent parallel work: 2.5-2.7x on three cores** when a level's work is ≥ 40 ms — ABOVE main's
  1.5-2.5x band and above the 1.76x the radix probe reached (that probe was memory-latency-bound; this one is
  register-bound, and 2.7x on 3 cores is 90 % efficiency). The ceiling of 3 is by policy (three A78 cores in
  the slot).
- **W = 1 ≈ serial (159 → 161-164 ms)**: one worker costs what the serial parent costs, so the spawn +
  futex machinery is not the tax it once looked like (the memory's conclusion stands). The exception is
  the many-small-tasks row, where W = 1 is 2.8x SLOWER than serial (142-152 vs 50-58 ms): 512 tasks each waking
  the parent's done-counter futex is a wake per 0.1 ms task; with W ≥ 2 the effect vanishes (65-75, 46-60 ms).
  OBSERVED, mechanism not isolated; the design consequence is clear regardless: **wake the parent once per
  level, not once per task** (a counter compared at claim time), and do not schedule tasks under ≈ 1 ms.
- **Sequential chains: 0.85x** (48-51 → 58-60 ms): main's ~1x confirmed, the 15 % is 24 barriers at ≈ 0.4 ms
  each when nothing else runs — the price of a scheduler on a workload that has no parallelism, and the
  reason a chain-shaped projection should be ONE node.
- **Determinism**: the fold was identical at W = 0, 1, 2, 3 in all 40 runs of §3.2-3.3.
- **Minimum useful node**: from the barrier cost (≈ 0.4 ms idle, ≈ 1.5-2.5 ms under load) and the spawn floor
  (1-5 ms), a level must carry ≥ ~10 ms of work per worker for the DAG to pay; below it, run the level
  serially in the parent (the W = 0 path is the same code). Against §12.3, EVERY dowiz kernel at 165 dishes

## 7. The full DAG runtime: design

Operator decision 2026-09-28: bebop is rewritten onto a full DAG runtime. This section designs it against what
the tree is (§1) and what the box measures (§2-4). Where a number decides a design choice the number is cited.

### 7.1 Node granularity: function, object, projection — never expression

| Node kind | What it is | Key (content hash) | Why this grain |
|---|---|---|---|
| **compile node** | one top-level `fn` (bebop has no closures, no nested fns — `arch_check` nested-fn) compiled to position-independent words + a relocation list | `H(compiler_digest ‖ fn_source_bytes ‖ callee_signatures ‖ ctor_table ‖ literal_slice)` | the compiler already visits the program fn by fn twice (`bebop.bp:7490-7560`); per-fn cost is what is left after the fixed floor went (ROADMAP A10) |
| **object node** | one store object (record, array, PartTab) | the object's `h0/h1` header already carries `layout_digest` + `crc32(payload)` + generation (`store.bp:3-5`); the node id is `sha256(layout ‖ payload)` when it must cross a machine (CAS), `crc32x` inside one image | already content-checked; a Merkle id costs ~1 µs/record (§11.1 MEASURED) |
| **projection node** | a pure fn from input object nodes to an output object node (a fold, a menu render, an availability mask) | `H(code_version ‖ fn_key ‖ input_node_ids)` | this is dowiz's twelve projections and bebop's `kv_snapshot`/log fold; the granularity at which "incremental == full" can be checked |
| **effect node** | an `io` fn whose only output is a RECORD appended to a log (outbox pattern) | same as projection; replay-safe by the idempotent record id | effects as data: the log is the only side effect, so replay is a fold |

Expression-level nodes are excluded by measurement: the cell substrate cost 41x on dense work and won only
under 0.39 % change (§1.1 last row). A DAG whose nodes are functions and objects keeps every inner loop as
straight-line machine code — the thing bebop is good at (K1H 1.8x Rust) — and puts the graph only where the
data already has edges.

### 7.2 Purity model: what a node may touch

bebop's state surface is small and enumerable: registers, the arena (`x27/x28`), `[i64]` cells reached through
handles, `str` bytes, and twelve Linux syscalls (`docs/LANGUAGE.md:94`; the wasm blueprint counted the same
twelve). One-cell mutables (`let x = x + 1`) are local rebinding and never escape a fn. So:

- **inputs** = the fn's parameters. A `[i64]` parameter the fn only reads is an input; one it writes (`a[i] =`)
  is an OUTPUT. The compiler already distinguishes the two for A8's index typing; the node signature records
  `(reads, writes)` per array parameter. `bpref.py`'s copy-on-write array bug (memory `bpref-oracle-can-be-wrong`)
  is exactly the discipline formalised: a callee's write into a parameter is a declared output edge, not a
  side channel.
- **allocation** (`zeros`) inside a node is node-local: the arena cursor is saved on entry and restored on exit
  (T126 already saves `x27/x28` in 9-symbol prologues), so a node leaves no allocation behind and its outputs
  are copied into their own objects.
- **syscalls** classify the node: none → `pure`; `sys_clone`/futex/atomic → `sched` (only the scheduler may
  use them); file/mmap/clock → `io`. T70 (`pure`/`io` effects, OPEN) is this table made a compiler check:
  a `pure` fn that dispatches a syscall builtin is refused at compile time, the way `sys_clone` with > 8
  kept symbols is refused today (exit 109).
- **the clock is an input** (dowiz `Req { now_ms }` rule): `clock_ms()` is an `io` builtin, so a projection
  that needs time takes it as a parameter and is `pure`.

### 7.3 Memo keys and the memo store

- Code version is part of every key: `compiler_digest` for compile nodes, `bebop.bin`'s digest ‖ the node fn's
  digest for projections. That kills "memo survived a deploy" and "bebop.bin != source" at once — the
  `.becache` already keys on the compiler's exact bytes (`bebop.bp:7940-7948`); this generalises it.
- Hash: `sha256_words` (software, `selfhost/prelude/sha256.bp`) for anything that crosses a machine or names a
  CAS block; `crc32x` (hardware, one instruction per cell) for in-process memo keys where a collision is
  caught by the `incremental == full` gate anyway. Measured throughputs in §2.4 / §11.1 decide which is
  affordable where.
- The memo store IS a bebop KV image (`kv.bp`): key = node key, value = output object bytes or the object's
  offset in the arena. Append-only with compaction (`st_compact`, Cheney), so eviction is "drop entries older
  than generation g at compaction" (LRU by generation) under a byte budget; nothing is ever overwritten.

### 7.4 The scheduler: parallel yet byte-identical

- Nodes are pure, so ANY topological order gives the same outputs. Determinism therefore needs only one
  rule: **outputs are assembled in node-index order, never in completion order.** Kahn's lowest-index-first
  order (`ordfsm.bp` already computes it for the FSM) defines the node index; the fold over outputs
  (`kv_snapshot`, the image bytes) walks indices.
- Ready set = the nodes whose inputs' generations equal the current ones; dirty set = nodes downstream of a
  changed input (the `changes_since` ring on the dowiz side; a per-node `deps` list here).
- W = 3 workers at most (three A78 cores in a slot; cores 0-3 are little and unused by policy), persistent
  for the run, claiming ready nodes with `sys_atomic_add` and parking on a futex between levels — the shape
  of `pool.bp`, measured in §3 with a levelled ready-set probe. The measured spawn+join floor (1 / 4 / 5 ms at
  W = 1/2/3) and the per-level barrier cost set the MINIMUM node size worth scheduling (§3.2).
- Each worker keeps ≤ 8 live symbols across the spawn (exit 109 enforces it) and receives its work through
  one `[i64]` environment cell block — the `sconc.bp` env idiom.

### 7.5 The permanent gate: incremental == full recompute, byte for byte

A new battery gate `dagfull`: for every fixture image and every projection node, (a) evaluate with the memo
warm after a random sequence of appends, (b) evaluate from the sources with the memo table EMPTY, (c) the two
output images must be byte-identical and their four-reader folds equal. `rebuild`'s `stale = []` on the dowiz
side is the same check; here it runs on every commit, not nightly. Mutation proof: skip one node's
invalidation and watch (c) go red. This gate is the one that makes the memo safe to ship; without it a memo
is a second account of the truth (companion report §3.4).

### 7.6 Fit with Lean and the four-reader fold

- Lean gets ONE new theorem, stated over the node graph, not over machine code: for pure nodes, every
  topological evaluation order yields the same output map (confluence of a finite DAG of total functions).
  That is a ~100-line Lean development over a `List`-indexed graph, and it is the whole scheduler proof —
  `sys_clone` stays unmodelled in the language semantics (`formal/README.md` names that gap honestly) because
  the theorem does not need it: it needs purity, which §7.2 makes a compile-time check.
- Per node, the existing machinery applies unchanged: the conformance harness (120/122) checks the fn's
  semantics; the four-reader gate becomes a per-node differential check (bebop.bin / Rust / wasm32 / Python
  each fold the node's OUTPUT object to one number). That is item 10 of the synergy list, at zero new tooling.

## 8. The one-jump replacement plan

Operator (2026-09-28, final): one jump, no staged migration, no second runtime beside the current one, no copy.
The plan below replaces the runtime whole in ONE change and shows correctness at the switch without a
parallel copy in the tree.

### 8.1 What "the runtime" is, precisely (so the jump replaces all of it and nothing else)

### 8.3 What must be true before the switch (preconditions, each a number)

1. `bebop.bin == compile(bebop.bp)` at the pre-jump commit (`arch_check` artifact-identity; §2.1 measured it TRUE today, `d1dedc62`).
2. The pre-jump commit's frozen artefacts exist for the whole 360-program sweep (selfhost 122 + std_tests 144 + parity_constructs 102 + neg; memory `sweep-122-is-not-enough`) — produced and hashed BEFORE the jump lands, from the pre-jump binary.
3. The four-reader fixtures (`crates/bebop-wasm/fixtures/kv.store`, `kv.expected`) and every `*.store` gate golden are unchanged by the jump by construction (the store format does not change; only readers do).
4. The battery is GREEN at the pre-jump commit (control first: memory `head-may-not-reproduce-its-own-artifacts`).

### 8.4 How correctness is shown AT the switch, with no parallel copy in the tree

- **Compiler**: the post-jump compiler must produce BYTE-IDENTICAL `.bin` for all 360 programs against the
  pre-jump commit's frozen outputs (git holds the pre-jump binaries; no second runtime in the tree, the
  comparison is against `git show <pre>:...`). Then `chain.sh --codegen` fixpoint gen3 == gen4. Then, for the
  memo: `dagfull`'s compile arm — compile each program cold, then after a one-line edit, then cold again; the
  warm output equals the cold output byte for byte (the becache gate's own rule, `becache_gate.sh`, now per fn).
- **Store**: for each fixture and each projection, warm-memo output == empty-memo output, byte for byte, and the
  four readers agree (`gate.sh`). The dowiz side's `rebuild.stale = []` on the QA hub is the same statement.
- **Scheduler**: W = 0 (serial) and W = 3 produce the same fold on every probe and gate (the dag probe of §3
  already checks it), run at least twice (memory `bebop-clone-kept-symbol-limit`: a threaded measurement runs twice).
- **Lean**: `lean_conformance` stays 120/122 and `Dag.lean` builds with 0 `sorryAx`.
- **Numbers**: the honest-twin rows (K1H-K4) and the store rows (G7/G8) must not degrade (gates outrank rows,
  memory `gates-must-improve-not-degrade`); §2/§4 give the expected gains the jump must show.

### 8.5 What the jump does NOT do

- It does not change the store FORMAT, the loader, the language surface or the emitted machine code for a
  program (only its placement/relocation step). Anything that changes emitted words for the same fn is a
  separate codegen commit (AGENTS L14, single-variable diffs).
- It does not port dowiz's Rust to bebop; bebop stays the bytes and the second reader (companion §5), now
  also the node-key definition every reader shares (§10 item 1).

**GDPR: a hash-addressed immutable store must still FORGET.** The tree already answered this for its own log
and the answer constrains CAS: `forget.rs:1-27` redacts a person's records IN PLACE, keeps `id` and `prev`,
sets a `REDACTED_BIT`, and appends a `Forgotten` declaration that conservation law 9 reconciles; it rejected a
rebuild (A: "changes every id after the first removed record, and the witness exists to contradict exactly
that") and crypto-shredding (C: "no cipher here ... history already in clear needs this anyway"). Under a pure
CAS, in-place redaction makes a block that no longer hashes to its name, and content-addressed sync would
re-fetch the OLD block from any peer that still holds it — the forgotten copy the operator's item 3 wants to
make impossible. So:

- **Blocks that hold personal data are the exception to "addressed by the hash of their bytes"**: their
  address is the id assigned at write (what `forget.rs` does today), the redaction is declared, and a peer
  that holds a block whose bytes do not match must accept the DECLARED redaction (a `Forgotten` record whose
  hash IS content-addressed) as the newer truth — i.e. the Merkle root covers ids, not bytes, for those blocks.
- **For NEW logs, crypto-shredding is the CAS-native answer and the cheaper one**: personal fields encrypted
  under a per-person key kept in a small MUTABLE key table (not CAS); forget = delete the key + append the
  declaration; every block keeps its hash and every peer's copy becomes unreadable at once. This is design C
  that `forget.rs` declined for existing clear-text history; it is right for a Box network where copies
  exist by design. Recommend: C for new logs from the jump, B kept for history. Which one: **crypto-shredding,
  with reachability-GC only for non-personal blocks** (GC cannot be the deletion mechanism for personal data —
  a reachable block is still a copy).

**Does a full switch to CAS block addressing make sense for a distributed Dowiz Box network?** For code,
media, catalogue versions, archived logs and projection outputs: **yes**, and it is mostly what exists
(content ids, content-addressed media, changed-chunk writes) given ONE key function (§10 item 1). For the
live log: it is a CHAIN, not a DAG, and CAS buys sync of its immutable prefix (EST: a Box that was offline
for a day fetches ~180 events × 54 cells × 8 B ≈ 78 KB, one chunk) at the price of the personal-data rule
above. What it does not buy: any speed on a request path — the fold cost (§4) is the same whether a block is
named by a hash or an offset. Cost: the key function (~60 lines × 4 readers), a mark-GC (~150 lines), a key
table + cipher for shredding (~200 lines; the tree has HMAC/PBKDF2 gated against RFC vectors,
`crates/dowiz-hub/src/crypto.rs`, and no AEAD — that is the one new primitive, KAT-gated like the PQ code).

### 11.2 (B) Zero-deserialisation layout

- **Premise "on-disk = in-memory = on-wire" holds INSIDE a bebop process today**: the store is mmapped, a
  `ref` is an object-relative cell offset, `st_cells`/`st_addr` are identities (`store.bp:6-9`), and the
  memory note `bebop-is-dowiz-database` records that this is what lets Rust read the same bytes.
- **Across the Worker boundary it cannot hold**: a wasm module's linear memory is copied to and from JS
  (`Response` bodies, `get_multiple` results); there is no mmap in a Worker; the Rust reader `Store::from_bytes`
  COPIES the image into `Vec<i64>` cells (`crates/bebop-store/src/lib.rs:144-150`). §4 MEASURED that copy:
  **31 ms for a 2.9 MB log image, 5x the 5.75 ms fold it feeds**; and the KV image is 8x its payload because
  the layout stores one byte per cell (§4). So "zero-deserialisation" on the Rust side is two fixes away:
  the v2 byte packing for KV, and a reader that borrows `&[u8]` instead of copying into `Vec<i64>` (a
  `from_le_bytes` per access — the `view_price` shape §13.2 measures).
- **What is actually parsed on the hot paths is JSON, not the image**: 2,750 `json!`/`serde_json` sites
  (COSTS §2); `bom_of` parses each product's JSON per order line (`stock.rs:1386-1409`); the catalogue is
  parsed whole in the Worker at ~40 `load_catalog` sites (companion §1.4.4). §13 measures the parse share:
  JSON parse of a 165-dish catalogue vs the kernels that consume it vs a columnar block's decode/view.

### 11.3 (C) Temporal branching / state forking

- The store keeps generation g and g-1 (two superblocks) and has commit-object and heads-table cells
  reserved (`store.bp:10-11`, "C3"); `docs/RESEARCH-BYOK-ECS-DATAFLOW-2026-09-08.md` §0.7 costs named
  branches + `st_open_at(gen)` at ~60-100 lines and notes there is no undo/redo log to fight.
- Fold determinism makes a fork a REPLAY with substituted inputs: fork = a new root that shares every object
  with the parent (zero copy, the arena is append-only), substitute the catalogue node (price/recipe/discount
  matrix), re-fold the last N days' real orders through the same `decide` functions, read the projections
  (revenue, stock consumption, refusals), discard = drop the root. No demand is invented: the replayed
  demand is the recorded one, so the result is "what the same customers would have paid / consumed".
- Cost on a DO: one projection evaluation per scenario = one full fold of the window (§4: ms per 5,400
  events) plus the scenario's catalogue node; size = the substituted node only (the shared prefix is free).
  The rendering of the comparison is a projection too (§10 item 8's provenance walk).

## 12. Datalog layer and tensor/SIMD layer: designs and measurements

### 12.1 (D) The reactive Datalog layer — design (operator: mandatory)

**Where the core lives.** In bebop, as a library over the store's CSR/bucket indexes, compiled to the SAME
node graph as everything else: a rule is a projection node whose inputs are the relations it reads and
whose output is the relation it derives. `qdsl.bp` (parser) and `qplan.bp` (join order for k ≤ 4 tables,
dense accumulators, CSR choice) are the seed; what they lack is (a) recursion, (b) negation, (c) an
incremental step. The surface stays imperative (Eve's lesson, §11.4): rules are DATA (a relation of rules,
`head ← body`), declared beside the edge table, and the compiler turns each into a bebop fn via `gen_gb`'s
template path (`selfhost/std/gen_gb.bp`, the kernel generator that `gb_run` compiles in-process).

**Evaluation.** Semi-naive over the dirty set: for a stratum, `Δhead = body[Δinput]` — for every body atom
that changed, join its delta against the current full relations and add the new facts; iterate to a
fixpoint inside the stratum (recursion) with the delta from the previous round only. The dirty set is the
node dirty set of §7.4 (a changed stock cell → the supply's column in the dish×supply CSR → the dishes
whose availability may change). This is exactly `delta_avail` in §12.2, measured per event.

**Stratified negation.** Rules are grouped into strata by a dependency graph over predicates; a negated atom
must refer to a predicate of a LOWER stratum (no negation through recursion). The stratification is computed
at compile time by the same Kahn order `ordfsm.bp` uses, and REFUSED (a new loud exit code) when a negation
sits inside a cycle. Evaluation is stratum by stratum; a stratum's negated inputs are complete before it runs.

**Proof and gate.** Two things are proved once in Lean: (1) semi-naive over a monotone stratum reaches the
same fixpoint as naive evaluation (standard, over finite relations); (2) stratified negation is well-defined
when the stratification is acyclic — the theorem is over the rule graph, so it is the §7.6 confluence
theorem's sibling. Per rule set the gate is `dagfull`'s Datalog arm: after a random event sequence, the
incremental relation equals the relation re-derived from scratch, byte for byte.

**First rule set from dowiz** (each a projection over declared edges):

| Rule | Body | Delta trigger |
|---|---|---|
| `unavailable(D)` | `recipe(D,S,C) ∧ stock(S,Q) ∧ Q < C·q_min` | a stock event on S → column S |
| `allergen(D,A)` | `recipe(D,S,_) ∧ supply_allergen(S,A)` (transitive through `produced(S',S)`: recursion) | a recipe or supply edit |
| `fsm_ok(O,to)` | `state(O,from) ∧ allowed(from,to)` with `allowed` = the 14-edge table (`ordfsm.bp`) | an order event |
| `courier_may(C,O)` | `assigned(C,O) ∧ ¬ended(O)` (negation: `ended` is stratum 0) | an order or assignment event |
| `personal(N)` | `holds_person(N0) ∧ edge*(N0,N)` (transitive closure over the edge table) | a schema change; this IS item 3 of §10 as a rule |

### 12.2 (E) Prices and stock as integer tensors on SIMD — design

**Layouts (structure of arrays, integer minor units / grams / ppm, no floats):**

| Tensor | Shape | Type | Note |
|---|---|---|---|
| recipe | dish × supply, CSR (`row_ptr[D+1]`, `col[nnz]`, `coef[nnz]` grams) and, for the vector path, DENSE D×S i32 | i32 | 165 × 120 = 19,800 cells = 79 KB dense; nnz ≈ 350 |
| stock | supply | i32 grams (or i64 when a supply can exceed 2^31 grams — 2,147 t; not a restaurant) | one column |
| lots | lot × {supply, left, expiry} | u32 / i64 / i32 | sorted by (supply, expiry) so "first-expiry-first-out" is a segmented scan |
| price | dish × {base, modsum, tax_ppm} | i64 | tax needs 64-bit intermediates: 21,000,000 minor units × 1.2e6 ppm overflows i32 |
| modifiers | dish × modifier, CSR | i64 | |

**Overflow rules.** Checked i64 everywhere money is touched (dowiz money law); the vector kernels are only
allowed where the bound is provable from the types (i32 grams × i32 q ≤ 2^31 when q ≤ 10 and grams ≤ 2^27),
and the scalar reference kernel is the oracle: both run, both folds must be byte-identical (§12.3 asserts it).

**Determinism across SIMD and scalar.** Integer SIMD is exact, so the only way the two differ is a different
rounding rule or a different overflow behaviour; wrapping vs checked is the risk and is closed by the
bound above plus the fold comparison. Division is the trap: **there is no integer division in wasm SIMD nor
in NEON**, so any kernel written as `stock / coef` scalarises — availability must be asked as
`coef × q ≤ stock` (a mask), and "how many portions" stays scalar or becomes a small fixed loop of
compare-and-subtract. Tax is a division by a constant (LLVM turns it into a multiply-high; there is no
i64 multiply-high in simd128 either, so the i64 price kernel does not vectorise — §12.3 shows it).

**bebop codegen for v128.** None exists (`bebop.bp` emits NEON only inside `hvham`/`hvham2`); a vector
register tier is a new emitter with its own register model (T64 "use the silicon this box has", OPEN) and is
NOT part of the one-jump runtime replacement (§8.5). On the Box the kernels are Rust (the same `dowiz-hub`
crates the Worker links) until bebop has one.

## 13. The universal codec: design and measurements

### 13.1 Design: an Arrow-like block that is at once the CAS block, the wire format and the memory format

A block = header (`magic`, `n`, `nnz`, one length per column) + columns, each a typed little-endian array:

| Type | Encoding | SIMD-able ops |
|---|---|---|
| numbers, money, weights | i64 / i32 columns | add, cmp, min/max, mul (i32 lanes; i64 mul in simd128) |
| text | u8 byte tensor + u32 offsets (one per string) | UTF-8 validate, search, compare, sort keys (simdutf-style) |
| logs / ragged records | offsets + values (the evlog's `payload_len ‖ payload` frames are this already) | scan, filter |
| relations, the DAG, the FSM | CSR (`row_ptr`, `col`, `val`) and transition tables (`allowed[from]` bitmask) | gather; a branch becomes `mask ← cmp; select(mask, a, b)` |
| optional fields | values + validity bitmask | and/or of masks |
| JSON at the edges | a parser/serialiser to and from the block (simdjson-style on the Worker side is a Rust crate; on bebop's side `minijson`'s shape) | only at the boundary |
| hashes / CAS ids | sha256 over the block bytes (multi-buffer when many blocks) | |

Round-trip gate per type: `decode(encode(x)) == x` byte for byte and `encode(decode(b)) == b`, run in the
battery over every fixture; the scalar reference kernel is the oracle for every vector kernel. Money stays
i64 minor units. **How branch-heavy logic is tensorised**: both arms are computed over the whole column and a
mask selects (`mask_dense_vec` in the probe is the shape: `bad |= (coef != 0) & (coef·q > stock)`), which
costs both arms always — a win only when the arms are cheap and the column is long, a loss for the order FSM's
decide (one order, 14 edges, a branch per event): there the "tensor" form is the bitmask table lookup
`allowed[from] >> to & 1`, which is what `FSM_ADJ` already is (`order_machine.rs:216-222`).

Where the tensor path wins, is neutral, and loses:

- **Wins, by two to three orders of magnitude, at the codec — not at the kernel.** At 165 dishes the JSON
  parse (6.33 ms) is **760x** the kernels it feeds (8.3 µs) and **2,600x** a block decode (2.4 µs); a
  placement's five `bom_of` parses (41 µs) are 500x a delta step (82 ns). The Free-plan kills cluster where
  the catalogue is parsed (companion §0.5); a block that is the wire and memory format removes 99.9 % of
  that CPU. This is the same conclusion as the companion's R2 ("the parse moves to the object, once per
  catalogue change") with the parse itself made 2,600x cheaper on top.
- **Neutral on the kernels themselves** (§12.3 items 2-3): the arithmetic is microseconds in any layout.
- **Loses where the tensor is dense over a sparse relation** (§12.3 item 1: 8x at 1x, 580x at 100x) and where
  branch logic is turned into both-arms-plus-select over a short column (the order FSM: one order, 14 edges
  — the bitmask lookup that `FSM_ADJ` already is beats any column form; a 12×12 transition table is 144
  cells, not a workload).
- **The CAS cost is the hash, and it is the hash of the BLOCK, not the JSON**: 30 µs vs 1.54 ms at 1x
  (52x, the size ratio). Per event 1.55 µs — 0.3 % of the 500 µs durable commit (ROADMAP G7).
- **Conversion at the edges**: encode 2.0 µs + decode 2.4 µs = the whole round trip is 0.07 % of one JSON
  parse; a JSON serialiser is still needed at the browser edge (398 µs per full menu today; a columnar
  block plus the replica's own render, §10 item 2, makes that a client cost).
