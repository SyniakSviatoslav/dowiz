## 0. The answer in ten lines

1. **On Cloudflare dowiz already has the SHAPE of "microkernel + sandbox per tenant", minus the proofs and minus
   per-module sandboxes.** Every request runs in a V8 isolate executing one wasm module; every venue is its own
   Durable Object with its own storage, "P67's hub-per-tenant arriving as a property of where the bytes live"
   (`workers/api/src/hubdo.rs:104-107`); the object is "NOT REACHABLE FROM THE INTERNET" (`:1978-1981`); the
   capability set is closed, seven bits, deny-by-default (`crates/dowiz-hub/src/caps.rs:27-36`, `:1147-1161`
   `admit`); the kernel's red-line policy is `DenyByDefault` (`crates/dowiz-core/src/ports/agent/scope.rs:265-283`).
2. **What Cloudflare does NOT give**: a formally verified kernel; isolation BETWEEN dowiz's own modules (ebills,
   fiscal, crypto, courier, storefront all share one linear memory and one set of secrets); sovereignty of the
   bytes (S3 nightly copies exist, `workers/api/src/cloud.rs`, but the live store is Cloudflare's).
3. **The Rust in the tree has zero `unsafe`** in `workers/api/src`, `crates/dowiz-hub/src` and
   `crates/bebop-store/src` (MEASURED, grep = 0 in each), so the intra-module threat is logic, not memory
   corruption. A per-module sandbox would isolate a panic and a credential, not a buffer overflow.
4. **seL4 in 2026 is realistic as the Box's kernel**: functional correctness, integrity and confidentiality
   proofs are complete on AArch64 (Proofcraft, 2026-08-21, DOC); the verified AArch64 configurations include the
   Raspberry Pi 4B and 5B, i.MX8M Mini/Plus/Quad, RockPro64 (DOC, `verified-configurations`); Rust userspace is
   official (`rust-sel4`: bindings, a Microkit protection-domain runtime, an HTTP-server demo; compatible with
   seL4 16.0.0 and Microkit 2.3.0, DOC); MCS is verified on RISC-V (2026-06-29) and being ported to AArch64.
5. **"WASM on seL4" is NOT realistic as a maintained thing in 2026.** WAMR's README lists no seL4 platform (DOC);
   wasmtime needs an OS; the seL4 Summit 2026 programme (35 talks and posters, DOC) contains no WebAssembly
   talk — the sandboxing work there is LionsOS "Carrels" containers, Pancake-verified drivers and Rust via
   HAMR. LionsOS itself "does not have a concrete verification story yet" and "is not expected ... to be
   stable" (DOC, lionsos.org, 0.4.0).
6. **A Box that a restaurant can use needs Ethernet + TLS + storage + a printer + Telegram.** On seL4 that is
   either LionsOS/sDDF components (research) or, the way Kry10 and the CHSS/Magnetite stack do it, **seL4 as the
   hypervisor with a Linux VM for drivers and the network** and the trusted parts beside it. The second is the
   only path with a product behind it in 2026 (Kry10 KOS: "C, Rust, Elixir, Erlang", "x64, ARM, Risc-V", BEAM as
   the main environment, DOC).
7. **What to adopt now (no new platform):** make the capability model reach the MODULE level — a declared table
   of which images each command may write (the DAG's edge table is exactly a capability manifest); split the
   credentials that do not belong in the storefront's memory (ebills, Stripe secret, Telegram bot token) into a
   second Worker reached over a Service Binding; build the Box as the static binary `Dockerfile` DK-08 already
   produces, with the store sealed (`workers/api/src/cloud/seal.rs`) and the same gates.
8. **What to defer:** seL4 until a Box pilot exists on a verified board (Raspberry Pi 5 is one); WASM-per-module
   on the Box until there is a module that is not already Rust in the tree; a wasm interpreter inside the Worker
   never (`docs/design/BLUEPRINT-BEBOP-IN-WASM-2026-09-23.md` §0.6: 15–20× slower, AGAINST).
9. **What never changes:** the crypto stays what it is — ML-KEM-768 + X25519 hybrid gated byte-exact against 80
   NIST ACVP vectors (`kernel/src/pq/hybrid.rs:1-13`), HMAC/PBKDF2 against RFC 4231/6070 vectors
   (`crates/dowiz-hub/src/crypto.rs:11-17`). No sandbox replaces a test vector.
10. **Costs** (HYPOTHESIS, §5): the two "now" items are lane-sized (days); a Box on minimal Linux is weeks; a Box
    on seL4-as-hypervisor is months and a person who has done seL4 before; a native seL4/LionsOS Box is a
    research project.

The honest summary: **dowiz's isolation unit is the venue, and it is strong; its isolation unit inside a venue
is a function call.** Brief (B)'s "WASM sandboxes per module (ebills fiscal, crypto, courier logistics)" is
asking for a unit the platform does not have.

### 2.2 The one place the shared module bites today

A Rust panic in any handler — an ebills parser fed a surprising page, say (`workers/api/src/ebills`, 7,588
lines with `fiscal` MEASURED) — is caught by worker-build's recovery wrapper, which reinitialises the wasm
instance (the main tree's build output `build/index.js`, gitignored: `__worker_init_state={criticalError:!1,instanceId:0}` and the
`Reflect.construct` re-instantiation proxy, MEASURED; worker-build 0.8.5 passes
`--experimental-reset-state-function --force-enable-abort-handler` to wasm-bindgen, its `src/main.rs:88-92`).
Cloudflare's own write-up: "for workloads that hold meaningful state in memory, such as Durable Objects,
reinitialization means losing that state entirely" (DOC https://blog.cloudflare.com/making-rust-workers-reliable/).
So a panic in the ebills poller running inside a venue's object drops that object's `mem` and `folded`
(`hubdo.rs:196-208`) — a performance event, not a security one, but it is the concrete cost of one module.
The fix Cloudflare ships is `worker-build --panic-unwind` (0.8.0+, same post), which needs nightly + `-Zbuild-std`
(DOC, rustc wasm32 page) and is discussed in `2026-09-27-binary-size.md` §3.

## 3. What "seL4 + WASM" would be, concretely, and what each piece costs

### 3.1 seL4 facts (DOC, 2026-09-27)

- Verified properties by architecture (https://docs.sel4.systems/projects/sel4/verified-configurations.html):
  **AArch64** (kernel in EL2, FPU yes): C-level functional correctness incl. fast path, integrity and
  availability, confidentiality; platforms include Raspberry Pi 4B, Raspberry Pi 5B, Odroid-C2/C4, ROCKPro64,
  i.MX8M Mini/Plus/Quad, i.MX93, TX1/TX2, ZCU102/106. **AArch32**: the most complete (binary correctness too).
  **RISC-V 64**: functional correctness, integrity, confidentiality; no fast path. **x64**: functional correctness
  only. "none of our verified configurations take into account address translation for devices (System MMU or
  IOMMU), debug/profiling/printing interfaces, or the kernel startup at boot."
- Proofcraft 2026 (https://proofcraft.systems/news-2026/): security proofs complete on AArch64 (21 Aug 2026);
  MCS functional correctness on RISC-V (29 Jun 2026), port to AArch64 under way; dynamic domain scheduler in
  seL4 15.0.0 (1 Jun 2026); a 250k-line proof reduction (21 Sep 2026).
- Microkit (https://docs.sel4.systems/projects/microkit/): "a small set of simple abstractions that ease the
  design and implementation of statically structured systems on seL4"; protection domains, channels, memory
  regions; maintained by Trustworthy Systems.
- Rust (https://github.com/seL4/rust-sel4, README updated 2026-07-22): `sel4` bindings, `sel4-root-task`,
  `sel4-microkit` "a runtime for seL4 Microkit protection domains", `sel4-async-*` (experimental), CapDL
  initialiser and kernel loader in Rust; "not yet hosted on crates.io"; nightly toolchain
  (`nightly-2026-08-21`); demos: root task, Microkit system, **HTTP server** on Microkit
  (https://github.com/seL4/rust-microkit-http-server-demo).
- LionsOS 0.4.0 (https://lionsos.org/): "currently undergoing active research and development, it does not have a
  concrete verification story yet"; components joined by Microkit, lock-free queues, "the system is static: it
  does not adapt to changing hardware, and does not load components at runtime". sDDF Ethernet "capable of
  strong performance" since 2022 (Summit 2026 abstract); filesystems and a firewall exist as LionsOS components
  (Acacia abstract).
- Kry10 KOS (https://www.kry10.com/): seL4-based, "C, Rust, Elixir, Erlang", "x64, ARM, Risc-V", "two main,
  first-class environments ... direct APIs for drivers or highly performance sensitive applications written in C
  or Rust ... [and] the Erlang BEAM"; a Software Safety Manual presented at the 2026 Summit.
- The 2026 Summit programme mentions Rust (CHSS/Magnetite "written in Rust", a Rust VMM, HAMR Rust
  generation) and containers (Carrels on LionsOS) and **no WebAssembly** (MEASURED: `grep -i "webassembly\|wasm"`
  over the abstracts page = 0 hits).

### 3.2 WASM runtime facts (DOC)

- WAMR (https://github.com/bytecodealliance/wasm-micro-runtime): interpreter/AOT/JIT; "core vmlib on cortex-m4f
  ... ~58.9K for fast interpreter, ~56.3K for classic interpreter, ~29.4K for aot runtime"; platforms named in
  its tree and CI include Linux, Windows, macOS, Zephyr, ESP-IDF and others; **seL4 is not among them**.
- wasmtime (https://github.com/bytecodealliance/wasmtime): Cranelift AOT/JIT; a hosted runtime that expects an
  OS (std). Feasible on Linux on the Box; not on a bare Microkit PD.
- Cloudflare: "Threading is not possible in Workers"; "SIMD is supported"; WASI "experimental ... only some
  syscalls implemented" (https://developers.cloudflare.com/workers/runtime-apis/webassembly/).
- The tree already compiles the room deciders to wasm32 without wasm-bindgen: `crates/bebop-wasm`
  (`--features decide`, `.github/workflows/ci.yml:54-57`), "so a tablet offline and the venue's object decide the
  same bytes" (`crates/dowiz-hub/src/room/amend.rs:23-25`). That module is the natural first thing a Box would
  host in a sandbox — and it is Rust already, so the sandbox would isolate nothing the type system does not.

### 3.3 The three Box architectures, and what each costs (HYPOTHESIS unless marked)

| Architecture | What runs where | Drivers / network / TLS | Proof coverage | Cost | Verdict |
|---|---|---|---|---|---|
| **B0: static Rust binary on minimal Linux** (what `Dockerfile` DK-08 + `docker/mkosi-rootfs.sh` build) | `native-spa-server` + files; sealed store; nightly to S3 | Linux | none, but the smallest step from today | weeks: packaging, first-boot claim, printer, updates | **adopt when the first Box customer exists** |
| **B1: seL4 as hypervisor + Linux VM + dowiz native beside it** (Kry10's and CHSS's shape) | Linux VM owns NIC/TLS/printer; dowiz in its own PD or VM; the signing key and the store in a PD Linux cannot read | Linux VM (unverified path), seL4 VMM | kernel proofs (AArch64); the isolation between the Linux VM and the store PD is what the proofs buy | months + one engineer who has shipped seL4; a verified board (Pi 5 / i.MX8M Plus) | **the realistic "sovereign Box"**; defer until B0 has a customer |
| **B2: native seL4/LionsOS, sDDF drivers, Rust PDs, WAMR/wasmtime for modules** | every module a PD; wasm modules under a runtime that would have to be ported | sDDF Ethernet (research), TLS in Rust `no_std` inside a PD, block/fs from LionsOS, printer: nothing | best, but LionsOS has "no concrete verification story yet" | a research project | **AGAINST in 2026**; re-entry when LionsOS is stable and a wasm runtime exists on it |

What B1 actually protects in dowiz's terms: the store (`orders.store`, `stock.store`, ...,
`tools/native-spa-server/src/hub.rs:40-58`) and the token signing key (`signing.key`, "must never travel with a
backup of the data", `:53-56`) live in a protection domain the network-facing Linux VM cannot read; the VM can
only speak to the store PD over a Microkit channel that carries commands (the same `command::send` shape,
`workers/api/src/command/mod.rs:229-236`) — i.e. the DAG's edge becomes an IPC channel and the node's memory is
capability-isolated. That is a real property, it is the property seL4's proofs are about, and it needs no WASM.

## 4. What to adopt NOW on Cloudflare (no new platform), with file:line

1. **Capabilities at the module level — a declared write manifest.** Today `Caps` scope PEOPLE; nothing states
   which images a command may write. The DAG's edge table (`2026-09-27-dag-architecture.md` §7 Phase 4) is that
   manifest: `(command, inputs, images written)`. Enforce it where the write happens — `put_image`
   (`hubdo.rs:1878`) takes the image id; a command turn that writes an image not in its row is refused in a
   test, and `tools/gates/one-image.sh` already counts "handler bodies write more than one image". Lane-sized.
2. **Secrets out of the storefront module.** `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `TELEGRAM_BOT_TOKEN`
   and the ebills credentials (stored per venue in the `ebills` Table, `hubdo/ebills.rs:59-71`) are readable by
   every handler in one wasm module. Cloudflare's native module boundary is a **second Worker behind a Service
   Binding** ("Use Service Bindings to send requests from one Worker to another on your account without going
   over the Internet", DOC limits page). A `dowiz-rails` Worker owning Stripe, Telegram and ebills, with its own
   secrets and a fixed request shape, gives the "sandbox per module" the brief asks for on the platform's own
   terms. Cost: a second crate, a second deploy, +1 subrequest per send; the outbox drain already runs on a
   timer, so latency is not on the customer's path. Note `tools/gates/one-image.sh` and the clock gate apply
   unchanged. Memory `native-spa-server-is-a-second-worker` records the trap: shared function names across two
   binaries must live in one crate (`crates/dowiz-hub`), never be copied.
3. **`--panic-unwind` evaluation** (companion binary-size doc §3): keeps object memory across a panic in one
   handler; needs nightly + build-std; measure size and CPU before adopting.
4. **Sign the chain.** `actor_pubkey` is zero on every append (`hubdo.rs:1578`). The kernel carries an
   ML-DSA-65 primitive (`kernel/src/lib.rs:25` "OPT-IN post-quantum crypto core (ML-DSA-65 / ML-KEM-768 /
   X25519 / AES-GCM)") and a per-call signer built on it (`crates/dowiz-core/src/crypto_signer.rs:1-14`), and
   the capability path names "Ed25519 ⊕ ML-DSA-65" (`crates/dowiz-core/src/ports/agent/cap.rs:11-17`); none of
   it signs the order log today (the earlier bench-only signed-log module recorded in memory `AUDIT-ITEM-22` is
   no longer at its cited path — where it went is unverified). A signed tip per rotation (`log@<gen>` archives,
   `workers/api/src/hubstore.rs:1046`) is the cheapest first step and is what a sovereign Box would verify against
   a cloud copy. (Operator decision: PQ = option B, memory `dowiz-pq-and-investment-decisions`.)

## 5. What to defer, and the re-entry condition for each

| Item | Defer because | Re-enter when |
|---|---|---|
| seL4 Box (B1) | no Box customer; B0 gets most of the surface reduction | a venue asks for the bytes to stay in the building, and B0 has run for a month |
| WASM per module on the Box | every module is Rust in one tree; a sandbox isolates nothing the compiler does not, until a third party's code arrives | a plugin that is not dowiz's (a fiscal printer vendor's module, a POS integration) |
| WASM per module in the Worker | wasm-in-wasm is an interpreter compiled to wasm: 15–20× slower (EST, BEBOP-IN-WASM §0.6) and a second copy of every type | never; the Service Binding is the platform's unit |
| Native seL4 (B2) | LionsOS is research; no wasm runtime on seL4; drivers for printers and Bluetooth do not exist | LionsOS stable + a verified TLS stack in a PD |
| Formal proofs of dowiz's own code | the kernel already has Kani wiring blueprints (`docs/design/BLUEPRINT-ITEM-07-kani-wiring-2026-07-19.md`) and the conservation laws run live | after the DAG's edge table exists, prove the table, not the handlers |
