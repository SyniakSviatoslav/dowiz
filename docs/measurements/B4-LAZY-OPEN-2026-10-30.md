# B4 — open + verify after N commits, the lazy open measured apart (W-ES-P10, 2026-10-30)

Status: MEASURED 2026-10-30 on the box (§2 before, §4 after the open-path change); x86 NOT MEASURED (no x86 here).

R-EMBED-STORE §4.6 row B4: "open+verify після 10⁵ комітів — ≤ 2 ms з якорем на x86 (O(останній
коміт)); без якоря — назване число обходу". §12 P10's exit: B4 ≤ 2 ms with the anchor on x86, a
named number on the box, and a T-ES where corruption in an OLD commit is caught by `verify(Full)`
and NOT by open (`crates/bebop-io/src/db/lazy_tests.rs`; `tools/gates/conformance.sh --lazy`).

## 1. What is measured, and the command

`crates/bebop-io/examples/b4.rs`: a v4 (B+tree) store of N single-put commits in a file
(`Durability::None`; the writes are not the row), then, `reps` times each, median and minimum:

| row | what |
|---|---|
| `open_anchor` | `Db::open_path` at `Verify::Anchor` (the DEFAULT): pick + PartTab crc + the anchor's crc over the last commit + `KvIn::open_lazy` -- plus, today, the file read and two copies of the image |
| `open_reachable` | the same at `Verify::Reachable`: every reachable object's crc |
| `open_whole` | the same at `Verify::WholeArena`: every object of the arena |
| `read_file` | `std::fs::read` of the image: the floor under every `open_*` above |
| `recover` | `sim::recover` over a `View` of the bytes: the anchor's crc alone, O(last commit) |
| `open_lazy` | `KvIn::open_lazy` over the `View`: the shape walk, no crc |
| `kvin_open` | `KvIn::open` over the `View`: what es-bench's `bebop` engine calls `open` (= its `verify`) |
| `walk` | `sim::walk` of the whole arena: `WholeArena`'s extra |
| `store_copy` | `Store::from_bytes` + `to_bytes_trimmed`: the two copies `Db::open` pays after the read |

The run also prints the recovered generation and `Via::Anchor { cells }`: the anchor's range IS the
last commit, and after a copy compaction that is the whole live set, so "O(last commit)" is only
small when the last commit was small. Each run says which it was.

```
cd crates/bebop-io && CARGO_INCREMENTAL=0 cargo build --release --offline --features tree --example b4
ulimit -v 2500000; target/release/examples/b4 <dir> 10000 5; then 100000 5
```
(through `bebop-lang/tools/slot.sh`, foreground; maxrss by `p10-runmeas.py`; n grown 1e4 -> 1e5).

## 3. What the numbers mean for B4's target

- THE PROOF IS O(last commit) AND IT IS 1 us: `recover` hashes the anchor's range (263 / 336 cells
  after 1e4 / 1e5 single-put commits) in 1 us at both sizes, and `KvIn::open_lazy` is 0 us. The
  verification half of B4 ("<= 2 ms with the anchor") is met on the box by three orders of
  magnitude; on x86 it can only be smaller. Unmeasured on x86 (no x86 here).
- `Db::open_path` at the default depth is NOT 2 ms: 4.6 ms at 1e4, 30.3 ms at 1e5. None of it is
  verification. It is the file read (5.1 ms at 1e5) plus the open path's copies: `read_cells` ->
  `Vec<i64>`, `cells_to_bytes`, `Store::from_bytes` (which PADS the trimmed image back to its
  arena capacity), then `to_bytes_trimmed` for the snapshot -- `store_copy` alone is 19.9 ms at
  1e5, two thirds of the open. So B4's remaining gap is a COPY problem in `Db::open`
  (`writer_of` / `Db::over`, bebop-io's open path), not a verify problem: build the writer's
  `Store` from the read cells without the bytes round trip and pad in place, and keep one trimmed
  copy for the snapshot (design D1); P14's mmap read path removes the rest.
- Reachable costs 1.46 / 13.6 ms over Anchor (the full crc), WholeArena another 0.4 / 2.7 ms:
  `verify(depth)` is where that is paid, explicitly, never on open.
- The anchor's range is small here because the LAST commit was one put; right after a copy
  compaction (130 of them in the 1e5 run) the last commit IS the whole live set and `recover`
  would hash all of it once -- the 1e5 run's last commit was not a compaction (`cells: 336`).

## 4. After the open-path change (same binary flags, same box, 1e5 commits, 11.7 MB image)

`Db::open` now reads only the snapshot's bytes (`db/lazy.rs`: the superblock pages, then the arena
to `arena_used`, as bytes through `Device::read_bytes`), runs `recover` over them, builds the
snapshot, and keeps the device; the WRITER (`Vec<i64>` padded to the arena's capacity) is built at
the first `begin_write`. Run line: `rc=0 wall=8.7s maxrss=244MB`.

| row | before, us | after, us | note |
|---|---|---|---|
| `open_anchor` (Db::open_path, default) | 30277 [29677] | **7486 [7194]** | 4.0x; of it `read_file` is 4737 [4408] |
| `open_reachable` | 44976 [42854] | 21872 [20495] | = open + `kvin_open` 13677 |
| `open_whole` | 47876 [47021] | 24830 [23362] | + `walk` 2775 |
| `recover` | 1 | 1 | the anchor's proof, O(last commit): unchanged |
| `store_copy` | 19948 | 20832 | no longer on the open path (the writer's, at the first write) |

What `open_anchor` still pays, by component: the file read (4.7 ms for 11.7 MB from the page cache,
~2.5 GB/s on this box), the lock file, `pick` + PartTab crc + the anchor (1 us), `KvIn::open_lazy`
(0 us), and ~2.5 ms unaccounted (the `Vec<u8>` growth in `live_bytes`'s second read and the `Snap`
allocation). It is linear in the LIVE image because the snapshot is a `Vec<u8>` the process must
hold; it is no longer linear in the arena's CAPACITY and it decodes, pads and re-encodes nothing.
The next step is not in this lane: a mapped `SnapImage` (P14, `snap.rs`), after which the open
reads the two superblock pages and the anchor's range and nothing else. W-ES-P8E's 330 MB row
(1046 ms before) should re-measure at roughly its file-read time; NOT MEASURED here.
