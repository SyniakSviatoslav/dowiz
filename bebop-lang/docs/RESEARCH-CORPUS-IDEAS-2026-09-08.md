## 0. Executive summary (10 lines)

2. **The strongest published argument against a current commitment is against the TRUST wording of zero-dependencies, not against zero dependencies.** `gen3 == gen4` is self-consistency; Thompson's attack survives any fixpoint by construction (1004.5534 "Fully Countering Trusting Trust through Diverse Double-Compiling"). The tree's own answer, T89 DDC via the attic'd `expr_compile.bp`, is OPEN (TASKS.md:100; no `tools/ddc.sh`, no `docs/TRUST-CHAIN.md`), so today's trust root is the checked-in 159,196-byte `bebop.bin`, which the 1,480-byte `seed/build/seed` merely mmaps and calls (seed.S:1-3), plus CPython for the bpref oracle. Fix costs zero dependencies (§7.1).
3. **The store's write path is the second-strongest case, and today's measurement is its empirical form**: 96 % of a CSR build in the file-backed page path (18,051 ms store vs 747 ms plain arrays, same result). Every survivor in the persistence literature -- LSM/log-structured stores, Metall (2108.07223: 11.7x on dynamic graph construction from allocator layout alone, abstract), write-combining radix sort (1008.2849: 88 % of peak bandwidth, abstract) -- builds scatter-heavy structures in anonymous memory and publishes them sequentially. "The file IS the memory image" survives for READS; for the build it is the bug (§5.2, row B8a).
4. **Blind area 1 -- memory-level parallelism in probe kernels (§3).** The join twin's probe loop is three dependent random loads per row (B2-decisive-twins.md §3(i)); frontier BFS runs at 23-45 ns per edge slot against a 0.67 ns/slot bandwidth floor (12 GB/s / 8 B), i.e. latency-bound by a factor 35-70. Cimple (1807.01624), CoroBase (2010.15981), Cuckoo Trie (2201.09331, "20 %-360 %" abstract), Calico's group prefetch (2604.00423) and DAE on big.LITTLE (1701.05478) all name the same lever: interleave G independent probes with software prefetch so the OoO core has G misses in flight. In bebop terms: one `prfm` builtin (1 word) plus an unroll-by-G template in `gen_gb.bp`. No IR, no dependency. LANG-DB:454's "prefetch is a sequential-stream mechanism" is the wrong model for this.
5. **Blind area 2 -- vertex relabelling for locality at compaction time (§4).** Reordering is the graph literature's cheapest locality win (1602.08820, 2001.08448, 2306.10410, 2409.04171) and the store already owns the two ingredients: a Cheney copy that assigns every offset (store.bp:355-416) and a BFS order it computes at 45 ns/slot. Derived, not measured.
7. **The 1.37x codegen gap at equal algorithm is already at the frontier the single-pass literature describes** (§5.1): TPDE (2505.22610) and copy-and-patch (2011.13127) place one-pass code "on par with" / "14 % faster than" LLVM -O0 (abstracts); bebop's honest rows (K8H 1.1x after A2b, K1H/K4 1.6-1.8x) are better than -O0-class against `rustc -O`. Nothing in the corpus moves that gap without an IR; the residual is per-loop words (the k8h diff is one `cmp #1` vs `tst`) and then scheduling, which the A78's OoO window hides. The corpus's real lever for the join is items 4-6: bytes and misses, not words.
8. **Against tensor-graph-as-database (§7.4)**: 1906.03113 says algebraic BFS does "many redundant operations over nonzeros" (bebop measured it: the dense `gb_mxv_generic` cannot replace the sparse frontier); 2502.13862 reports SuiteSparse:GraphBLAS losing 76x on loading and 13x/11x on edge deletes/inserts to a purpose-built dynamic representation (abstract); Graphulo (1606.07085) found "conditions that determine when" a graph algorithm is faster inside the database, not "always". The thesis survives as "CSR + semiring kernels for the traversal phases", not as the storage model for an update-heavy order log -- which B4's tail-COO/L0/L1 already concedes by building an LSM next to the matrix.
9. **Against B7's Selinger plan space**: worst-case-optimal joins (1203.1952, 1210.0481, Free Join 2301.10841, 1503.04169) run directly on sorted CSR -- a CSR is a two-level trie -- and are asymptotically better than any binary-join order on cyclic patterns (triangles, B3's `gb_tc`). This is a competing algorithm class with no row, not a planner tweak; it belongs to whoever owns B7 and is flagged, not proposed, here.
10. **The corpus's shape (§6) says bebop's niche has no active arXiv community**: the single-machine graph-engine wave is 2013-2019 (322 records in 201x vs 54 in 202x), persistence in the 2020s is LLM checkpointing, "language design" is the cs.LO backlog (108 pre-2010 records), "memory allocation" is small because `arena`/`bump` are rare words. Net: three rows worth an experiment (B2b MLP, B8a build-then-publish, B4b relabel), one conditional (A8b sub-32-bit), one open task revived (T89), zero new dependencies, zero IR.

## 3. Blind area 1: memory-level parallelism in the generated probe kernels

**What bebop has no row for.** Every kernel row on the roadmap is about words per iteration (A2b: 12 -> 9 words, K8H 1.8x -> 1.1x), registers (A1/A5/A6), cells (A8) or cores (B6). None is about how many DRAM misses are in flight. The measured kernels say that is the binding term:

- frontier BFS: 23 ns per edge slot in-process, 45 ns from the store (ROADMAP Measured; journal 1788760072). The bandwidth floor for an 8-byte slot at the measured ~12 GB/s is 0.67 ns. The kernel is 35-70x above the floor, so it is not bandwidth-bound; it is bound by the latency of the dependent gather `x[ci[k]]` (LANG-DB:539 already names the "1 line miss, ~10-20" per slot).
- the join twin (B2-decisive-twins.md §3(i)): `k = Rk[r]; for j in rp[k]..rp[k+1]: sum += Ra[r] * Sb[ci[j]]` -- per probe row, `rp[k]` is a random miss into an 8 MB array, `ci[rp[k]]` a second dependent miss, `Sb[ci[j]]` a third. An A78 can keep roughly a dozen misses in flight, but only if the addresses are in its reorder window; a dependent chain of three exposes them serially, and the loop-carried `sum` plus the inner `while` keeps the window short. This is the regime the abstracts describe.

**What the literature says (abstracts).** 1807.01624 "Cimple: Instruction and Memory Level Parallelism" (PACT'18): on "in-memory databases, key-value stores, and graph analytics ... compilers and hardware struggle to expose ILP and MLP", and the fix is tasks that "yield execution at annotated long-latency operations" and are "interleaved on a single thread". 2010.15981 "CoroBase" (VLDB'21): "lightweight coroutines ease the implementation of software prefetching to hide data stalls". 2201.09331 "Cuckoo Trie" (SOSP'21): an index "designed to have memory-level parallelism ... outperforms state-of-the-art indexes by up to 20 %-360 %". 2604.00423 (Calico, 2026): "group prefetch to exploit parallelism" for "irregular high-fan-out graph traversal access patterns". 2009.00202 "Helper Without Threads": "inline software prefetching ... for delinquent irregular loads". 1701.05478 "Decoupled Access-Execute on ARM big.LITTLE" is the same idea on this CPU family, split across core classes -- not proposed (one heavy slot, 32-process cap), but it confirms the mechanism is known to work on A-class cores. 1411.1460 "Branch-Avoiding Graph Algorithms" (30-50 % from mispredictions on BFS/CC, "x86 and ARM-based processors") is the sibling that the roadmap already holds under csel (A2b).

**Mechanism in this codebase's terms.** The kernels are generated text (gen_gb.bp, 12 templates), so the transformation is a template change, not a compiler pass:

1. one builtin, `prefetch(addr)`, emitting `prfm pldl1keep, [xN]` -- one word, a construct + bpref stub (bpref: no-op), no register-model interaction (it reads a register, writes nothing);
2. the probe template unrolled by G (G = 4 or 8): a first loop prefetches `rp[Rk[r+G]]` for the row G ahead; the second loop, one iteration later, prefetches `ci[rp[k]]` for the row G/2 ahead; the compute loop runs on rows whose three lines are already in L1/L2. This is "group prefetching" / AMAC in the DB literature and needs no coroutines: a fixed-depth software pipeline over an index array is plain straight-line code, which is what a one-pass compiler is good at;
3. for the frontier BFS the same template prefetches `x[ci[k+G]]` while processing slot k.

**Cost against the constraints.** Zero dependencies: none. One-pass: none -- the compiler gains one builtin; the schedule lives in the generator. i64: none. Word budget: the unrolled template is G x larger; the kernels are per-(op, semiring) and pre-JIT'd, so the compiler's own census does not move. Box: no extra process, no extra core.

**What it would become.** Row **B2b -- MLP in probe kernels** (attaches to B2's join twin and B3's frontier kernel). Gate: on the 1M x 1M join twin, both distributions, probe-phase ns per R row <= 1.2x of the Rust `HashMap` twin's probe (today the whole kernel is 0.67x of Rust-at-bebop's-algorithm, and the Rust best is a hash join, so this is the number that decides B2 (i) "≥ 0.7x best Rust"); on sgraph2, frontier ns/edge-slot <= 0.6x of today's 45 (store) with the fold unchanged.

**Cheapest experiment that kills it.** Hand-unroll the probe loop of `bench/vs_rust/std_tests/join_twin.bp` by 4 with a scratch `prfm` builtin (or, without any compiler change, emulate the prefetch with a dummy `let _ = rp[Rk[r+4]]` load whose result is folded into a dead accumulator) and measure inside `tools/slot.sh`. If the probe phase does not drop by >= 25 %, the loop is already at the bandwidth ceiling or the A78's own window already overlaps the misses, and the row dies before it is written. Second kill: if `perf_event_open` really is usable (C5's note: `perf_event_paranoid` reads -1 today), the L2-miss count per probe row before/after settles it in one run.

**Why this is not "helps row B2".** B2 is a measurement row with a gate; it names no mechanism for passing it. The other analyst's lens would find papers that help pick the twin; this one says the twin will lose to Rust's hash join on a mechanism no row addresses.

## 4. Blind area 2: vertex relabelling for locality, done by the compaction the store already has

**What bebop has no row for.** Vertex ids in the store are whatever the writer assigned (sgraph2 uses an LCG pair stream; W's order log will use arrival order). No row changes them. The graph literature's single cheapest locality win is to renumber vertices so that neighbours are near in memory, and it is normally an extra pass nobody wants to pay; here it is free, because the store's compaction is a Cheney copy that already assigns every object a new offset (store.bp:355-416, LANG-DB §0 item 8) and the BFS order that most reorderings want is what the frontier kernel produces at 45 ns/slot.

**What the literature says (abstracts).** 1602.08820 "Compressing Graphs and Indexes with Recursive Graph Bisection": "graph reordering is a powerful technique to increase the locality of the representations of graphs". 2001.08448 "A Closer Look at Lightweight Graph Reordering": hot-vertex reorderings "may inadvertently destroy the inherent community structure" -- a warning that degree-sort alone can lose. 2306.10410 "BOBA": a linear-time ordering that "can substantially speed up the conversion from a COO representation to the compressed format CSR" -- i.e. reordering also helps the build that §5.2 is about. 2012.10026: RCM reordering plus SIMD for BFS on Graph500 graphs. 2409.04171 "RCM++": RCM's starting-node heuristic. 2111.12281 (a bachelor's thesis, so weight it accordingly): "cache miss latency is responsible for more than half of the graph processing time". 2307.06305 "Diagonally-Addressed Matrix Nicknack": after RCM, ">95 % of these matrices fit into the DA-CSR format using 16 bit column indices" -- the bridge to §5.1. 1203.5675 "Memory Hierarchy Sensitive Graph Layout": hierarchical blocking across cache line, TLB entry and DRAM page -- relevant because this box has 4 KB pages, THP `[never]`, so a 10M-slot `ci` array is 20,000 pages against an A78 L2 TLB of roughly a thousand entries (outside knowledge, not from the corpus): TLB locality is a real term here, and relabelling is the only lever on it that an unprivileged process has.

**Mechanism.** A permutation `pi` (BFS order from a chosen root, or reverse-Cuthill-McKee, which is BFS with degree-sorted neighbours) applied during `st_compact`: `ci'[k] = pi[ci[k]]`, rows copied in `pi` order, `rp` rebuilt by the same counting pass the CSR build uses. Cost O(E) once per compaction, inside a pass that already reads every live object. Entities that carry the id (W's orders) get a forwarding cell in the migration table, which is the same mechanism §4d of LANG-DB uses for type changes.

**Cost against the constraints.** Zero dependencies: none. One-pass: none (data, not code). D0: none; a peer node reordering its own local store changes nothing on the wire if ids are content-addressed at the protocol layer, and MANIFESTO §2 says identity is `H(pq_pub || classical_pub)`, not a store offset. Caveat that decides the row: W is an order log, and time-of-arrival is already a good locality order for it; the win is for the graph phases (BFS/CC/TC over the order-courier-merchant graph) and must be measured there.

**What it would become.** Row **B4b -- locality relabel at compaction** (after B4 step 3, which owns compaction of versions). Gate: frontier BFS ns/edge-slot on the 1M/10M sgraph2 graph <= 0.7x after relabel with the fold identical; compaction wall <= 1.5x of today's 747 ms row; PK lookup unchanged.

**Cheapest experiment that kills it.** No store change: in sgraph2's generator, assign vertex ids in BFS order of the generated graph (a python oracle already computes `bfs_levels`) instead of LCG order, and rerun the frontier row once under a slot. If the ns/edge-slot moves < 20 %, random-id locality was not the cost and the row dies. If it moves, the store-side implementation is ~60 lines in st_compact.

## 5. The two measured bottlenecks, read against the literature

### 5.1 The 1.37x codegen gap at equal algorithm

**Where the single-pass literature puts the ceiling.** 2505.22610 "TPDE" (2025): "performs one analysis pass and then performs the compilation in just a single pass, combining instruction selection, register allocation, and instruction encoding ... compile LLVM-IR 8-24x faster than LLVM -O0 while being on-par in terms of run-time performance" (abstract). 2011.13127 "Copy-and-Patch": generated code "runs an order of magnitude faster than interpretation and 14 % faster than LLVM -O0", and "39 %-63 %" better than Liftoff on Coremark/PolyBench (abstract). 2305.13241 "Whose baseline compiler is it anyway?": "all Web engines have introduced new baseline compiler tiers", and value-tag overhead "can be reduced to near zero" (abstract). 2011.05608 "Efficient global register allocation": a lightweight allocator with a "future-active set", "at considerable runtime and memory cost" is what the classic algorithms pay for liveness (abstract). The corpus has no number for -O0 versus -O2; the well-known 2-3x is NOT from this corpus and is stated here as outside knowledge.

**Where bebop sits.** Honest rows: K8H 1.1x after A2b's three peepholes (journal 1788858343), K1H 1.8x, K4 1.6x, K3H 3.4x, K2H 3.3x (ROADMAP Measured), all against `rustc -O`, not -O0. The k8h word diff after A2b is nine words against Rust's eight, the difference being one `cmp #1` where Rust has `tst`. So on loop kernels bebop's one pass is already past the point the single-pass literature reaches, and the remaining 1.37x on the join is the class of thing (scheduling, unrolling, the i64 gathers) that no published single-pass technique addresses. Two honest reads of that:

- The corpus does not contradict the A12 refutation; if anything TPDE confirms the design point "one analysis pass + one emit pass" is the frontier and bebop already has the analysis (the `pure` arm pre-scan, the facts pass named in A12) without an IR.
- The corpus also says the gap will not close from the words side. Items §3-§5.1 are the levers: misses in flight and bytes per element. The 0.33x deficit is where bytes and misses live, not where instruction words live. Recommendation: stop spending codegen rows against the join gate after A2b; spend B2b.

**One small item with no row**: 2604.07902 "Optimization of 32-bit Unsigned Division by Constants on 64-bit Targets" (1.67x-1.98x on the microbenchmark, abstract; LLVM patch merged) -- bebop's `itoa`/`parse`/`sdiv base-2^k` paths divide by 10 with `sdiv`; a magic-multiply peephole for division by a literal is one vs_try_* arm of A2b's kind (~150 words) and is measurable on K5 (the parser). Not a row; a note for whoever next touches vs_binop.

### 5.2 Persistence is 96 % of a CSR build

**The mechanism as the code shows it.** `st_alloc` is a bump allocator that writes the header and returns an offset into the MAP_SHARED RW mapping (store.bp:169-177; `st_open` maps prot=3 flags=1 at :146 after `ftruncate` to the full size at :145). The CSR build's fill pass then scatters 10M `ci` writes and 1M `rp` writes over ~88 MB of that mapping (csr_profile_b2.sh header: "writes ~88 MB into a 512 MB mapping"). On plain `zeros()` arrays the identical scatter is 747 ms. So the 17.3 s is the difference between scattering into anonymous pages and scattering into file-backed shared pages of a sparse f2fs file. LANG-DB:112 measured the per-page cost: "first WRITE to a sparse f2fs page ~7.0 us/page; allocating file blocks on write is 3x an anonymous fault" and prescribed "pre-extend + pre-touch the store file in 64 MB steps". 22,000 pages x 7 us is only 150 ms, so first-touch alone does not explain 17 s; the candidates, in the order the literature ranks them, are (i) dirty-page writeback started by the kernel mid-build (Crotty et al. CIDR'22, cited in LANG-DB [w25]: "the OS may flush any dirty page anytime") re-dirtying and re-writing pages many times on flash -- `/proc/sys/vm/dirty_*` is unreadable here, `Dirty:` was 40 kB at idle, so this is testable only by sampling `/proc/meminfo` DURING a build; (ii) `st_seal`'s crc over 88 MB (2 x ~10 ms at 8 B/cycle, cannot be it); (iii) `st_commit_sync`'s msync of the appended range (store.bp:233-241: msync of the whole arena "cost 444 us per commit"; an 88 MB msync at the measured 0.6 GB/s is ~150 ms, cannot be it). The phase table the profile prints would have said which; it is not in the tree.

**What the literature says (abstracts).** Every design that ingests fast does not scatter into its durable pages. 2108.07223 "Metall": "data ingestion step is often more expensive than analytics"; an mmap-backed allocator with a Supermalloc-style layout gave "11.7x ... over Boost.Interprocess" on "a dynamic graph construction workload" -- the same kind of workload, the win from allocator layout, not from hardware. 1008.2849 "Faster Radix Sort via Virtual Memory and Write-Combining": a counting sort (which `csr_build` IS) reaches "at least 88 % of the system's peak memory bandwidth" by "taking advantage of virtual memory and making use of write-combining" -- i.e. scatter through small per-bucket buffers so that each destination line is written once, whole. 2602.01873 "Tidehunter" and 1207.0140 "LogBase": the log is the store, values "are never overwritten", indexes are "small, lazily-flushed". 2310.16300 "Snapshot": page-level dirty tracking in msync causes "write amplification", fixed by user-space tracking of what actually changed. 1109.6885 (SAP, VLDB'12): read-optimised stores take writes into a "write-optimized delta partition" and merge -- the B4 tail-COO design is exactly this, which is the reason it will not have this problem for updates; the BUILD is the case B4 does not cover. 2603.01384 "Unix Tools and the FITO Category Mistake": "no syscall-based persistence primitive can define a commit boundary under failure" -- relevant to B1's wording only; the tree already says power-loss durability is unprovable on `fsync_mode=nobarrier` (LANG-DB §0 item 4).

**What it would become.** Row **B8a -- build in RAM, publish sequentially** (before B8, because B8's ingest is this build at W's scale). Mechanism: the CSR build allocates `rp`/`ci` as plain arrays (anonymous mapping, exactly the 747 ms arm), then `st_alloc`s two objects and copies them in one sequential pass (88 MB at DRAM copy speed, ~20-40 ms), then seals and commits as today. If the scatter must be write-combined for the plain arm too, 1008.2849's bucket buffers are ~40 lines. The thesis sentence is preserved for every READ ("persisted objects are in-memory objects, same layout, object-relative offsets") and weakened for exactly one write shape: bulk construction. That weakening is the design of LMDB, SQLite's WAL, every LSM and Datomic -- all of which LANG-DB §1 lists as the survivors. Gate: store arm <= 1.3x plain arm on the 1M/10M build (<= ~1 s where today is 18 s); G8's "build the CSR 44.8 s" row falls accordingly; fold identical. Cheapest experiment that kills it: change `csr_build_profile.bp` so `rp`/`ci` are `zeros()` during the build and copied into `st_alloc`'d objects at the end (~15 lines, no compiler change); if the store arm does not fall below 2 s, the cost was never the scatter path and the diagnosis above is wrong -- then sample `/proc/meminfo` `Dirty`/`Writeback` every 100 ms during the original build to test (i). Cost: zero-dep none, one-pass none, box none (the plain arrays are already allocated in the arm that takes 747 ms).

**What is NOT proposed**: userfaultfd-based paging (UMap 1910.07566 -- a runtime), huge pages (THP is `[never]` here and unprivileged), `MAP_POPULATE` of 512 MB (the file is sparse; populating allocates blocks for pages never written), a WAL (refuted, and the store's append-only arena IS an after-image log).

## 7. The strongest published arguments against what bebop is committed to

### 7.1 Zero dependencies as a TRUST argument (strong against the wording; the fix adds no dependency)

The claim as stated ("the trust argument rests on those 159 lines of assembly") is not what the tree implements. seed.S:1-3 is "a FROZEN Bebop loader ... openat -> lseek size -> mmap(PROT_RWX, MAP_PRIVATE) -> arm arena -> call": it loads and jumps to `bebop.bin`, a 159,196-byte checked-in binary. `gen3 == gen4` proves that `bebop.bin` reproduces itself from `bebop.bp`; it cannot distinguish a faithful compiler from one that recognises its own source. That is Thompson's construction and the corpus states the only two answers: 1004.5534 "Fully Countering Trusting Trust through Diverse Double-Compiling": "even complete analysis of a system's source code will not find the malicious code ... DDC can determine if source code and generated executable" correspond, by compiling the source with an INDEPENDENT compiler and comparing the fixpoints; and 2508.12054 "Certified Compilation based on Goedel Numbers": "certificates ... that a binary image faithfully represents the source code", explicitly positioned against DDC and translation validation. 2202.09231 "Camlboot" shows the archaeological alternative's cost (a stacked reference interpreter to remove OCaml's opaque bootstrap).

The tree knows this: T89 (HISTORY.md:2277-2285) specifies DDC with the attic'd `selfhost/attic/expr_compile.bp` as witness ("witness compiles bebop.bp -> W1; W1 compiles bebop.bp -> W2; W2 must equal the golden fixpoint byte-exact"), with `tools/ddc.sh` and `docs/TRUST-CHAIN.md` as deliverables. Today: TASKS.md:100 `T89 | OPEN`; neither file exists; the witness "must still compile the current surface", and the surface has grown by struct literals, `use`, `ref T`, `scan`, `sys_run` since T45.

How strong: STRONG against the sentence "the trust argument rests on 159 lines of assembly" -- the honest sentence is "zero runtime dependencies; the trust root is one opaque 159 KB binary plus CPython (tools/bpref.py is the miscompile oracle for every gate) until T89 closes". WEAK as an argument for adding a dependency: DDC needs an independent compiler for the same language, and the witness can be the attic's own `expr_compile.bp` run on the same seed. What it costs: reviving a second compiler for a frozen subset of the surface -- T89's own blocker. What would move it: an operator decision on whether the trust claim is load-bearing for D0 (MANIFESTO C10 "crypto from-scratch, zero-dep" and §3.4 code-signing suggest it is: a signed `bebop.bin` whose provenance is a fixpoint is signed self-consistency).

### 7.2 One-pass compilation (medium; the corpus mostly supports the commitment)

The single-pass literature (§5.1) does not argue against one pass; it argues that the frontier is "one cheap analysis pass + one emit pass" (TPDE's exact description). A12's refutation measured the analysis pass's value on the compiler's own scanner loops (0-2 % of K5) -- it did not measure it on the fib-shaped code where the honest table still reads 3.3x (K2H, inlining and tail calls are the missing -O1 items) and it did not measure it on kernels, which are generated straight-line loops that need none of it. The strongest published counter-example to bebop's design point is copy-and-patch (2011.13127): it reaches -O0-class code with NO register model at all, by stitching pre-compiled stencils -- an existence proof that the register model is not where a one-pass compiler's quality comes from, and a design that bebop refused on principle (the stencil library is a clang output). Verdict: the commitment stands; the honest gap it leaves is recursion-heavy code, which W (loops over columns, an FSM as a 12x12 matrix) does not contain. If a future row ever needs inlining, TPDE's "one analysis pass" is the published shape and the A12 attic patch is the local one.

### 7.3 i64-only cells (strong for storage, weak for arithmetic)

The argument is arithmetic, not a paper: at 12 GB/s an 8-byte edge slot costs 0.67 ns of bandwidth and a 4-byte one 0.33 ns; today's join measurement attributes the non-codegen part of the 0.67x to "the price of i64-only arrays"; G7 loses 2.5x/2.1x on file size to sqlite's varints (ROADMAP Measured). A8 (u32) halves the storage cost and the roadmap already holds it. The corpus's contribution is that u32 is not the floor and that the next step has a law (§5.1's decode-throughput law, 2606.22423): with beta = 12 GB/s and T_dec ~= 2 values/cycle x 2.4 GHz = 4.8e9 values/s (the paper's portable-C decoder; bebop's would be ~1.4x slower), the ridge b* = 8 * beta / T_dec ~= 20 bits (portable) to ~27 bits (bebop scalar). So: u32 is bandwidth-bound and safe (A8 is right); 16-bit deltas on a scalar bebop decoder are decode-bound and would only pay with a NEON decoder (A9's `ld1`/`cmp_mask` territory); and the doctrine "scalars i64 only" is unharmed -- arithmetic in i64, storage at the width the law allows. Row **A8b -- delta/bit-packed `ci` after A8**, CONDITIONAL on A9: gate is bytes per edge slot <= 3 AND ns per edge slot not above A8's; cheapest kill: a 16-bit `ci` variant of the frontier BFS in sgraph2 (with `ubfx`, which A2b now folds into one word, and `ldrh`) measured against the u32 build -- if ns/slot rises, the law has spoken and the row waits for NEON.

### 7.4 Tensor-graph-as-database (medium-strong; the thesis survives narrowed)

Three published lines, each with a local measurement that agrees with it:

- **Algebraic traversal is not free.** 1906.03113 "Optimal algebraic Breadth-First Search for sparse graphs": "the many redundant operations over nonzeros ultimately lead to suboptimal performance" and masked SpMSpV "add work" beyond the optimum. Local: gb.bp's only tier-0 primitive `gb_mxv_generic` is a dense O(n) row scan and substituting it for the frontier kernel "would cost >>2x on every level with a small frontier" (journal 1788760072); the frontier kernel that wins (23-45 ns/slot vs queue 116) is Beamer's push/pull, which 1804.03327 shows can be expressed in GraphBLAS -- but as three separable optimisations with masking, not as "mxv".
- **The matrix is the wrong storage model for updates.** 2502.13862 (2025, abstract): SuiteSparse:GraphBLAS loses "76x in graph loading", "13x/11x in edge deletions/insertions" and "2.5x/2.6x in traversal on updated graphs" to a purpose-built dynamic representation. 2202.08808: "we are not aware of any dynamic SpGEMM algorithms in the literature" (2022). 2001.06935's 75 G inserts/s needs "hierarchical hypersparse matrices" -- a tiered structure, not a CSR. Local: B4 already replaces "the graph is a CSR" with tail COO + L0 + L1 + generations, i.e. an LSM whose lowest level happens to be a CSR. That is the right design and it is not the thesis sentence.
- **Relational engines closed the gap from the other side.** 1503.04169 "Join Processing for Graph Patterns: An Old Dog with New Tricks": "Selinger-style algorithms are asymptotically suboptimal for applications in graph analytics" and WCOJ lets "relational engines close the performance gap with graph engines"; 2301.10841 "Free Join" unifies WCOJ and binary joins with one data structure that "unifies the hash tables and tries"; 1908.01812 gets WCOJ "directly from a representation that regards the relations as point sets in variable-dimensional grids, without the need of extra storage". A sorted CSR is exactly the two-level trie leapfrog triejoin (1210.0481) iterates; B3's `gb_tc` is a masked SpGEMM over `select(A, upper)` -- the WCOJ literature would run the same triangle count as a three-way intersection of sorted rows with no intermediate matrix. B7's planner ("join order (k <= 4)") is the Selinger space that 1503.04169 calls suboptimal for cyclic patterns. This is flagged for B7's owner, not proposed here.
- Graphulo (1508.07372, 1606.07085), the one published "GraphBLAS inside a database", reports (abstract) "the conditions that determine when executing a graph algorithm is faster inside the database" -- a conditional, from the group that created GraphBLAS.

Verdict: "a graph IS a sparse matrix and traversal IS a semiring product" is a correct statement about the traversal PHASES and about the oracle (LAGraph, 2104.01661); it is not a storage model for an order log that is inserted into a million times a day, and the roadmap's B4/B5 rows already concede that. The cheapest way to make the thesis sentence true and measurable is to say it for reads and let B4's log be the write model out loud.

### 7.5 "The file IS the memory image" (strong for writes, weak for reads)

§5.2 in full. The measured 96 % is the argument; the literature's unanimous answer is to build elsewhere and publish sequentially; the survivors LANG-DB §1 lists all do so. For reads the commitment is untouched (0.3 us page-cache fault, MAP_POPULATE 5 ms per 64 MB, LANG-DB:113).

### 7.6 The self-hosting fixpoint (weak as a critique, strong as a reminder)

The fixpoint is an invariant, "never a goal" (TG-DONE 2). The corpus's compiler-testing papers agree that the real oracle is differential: 1902.09334 (fuzzer-found miscompilations do reach real applications; "12 % of the historical" bugs studied over 309 Debian packages), 2007.08292 "NoREC" (evaluate the same query "by an optimizing and a non-optimizing version" -- this is what bpref.py is to bebop.bin, and what B3's tier-0 vs specialised kernel pair could be to gen_gb at zero cost: same query, two kernels, folds must agree; that is a B3 footnote, not a row). Nothing here argues against self-hosting; everything argues that the fuzz + bpref lane is the trust story, which puts CPython in the trust root (§7.1).

## 8. Smaller findings with no row (footnotes, not proposals)

- **Rank/select over the tombstone/mask bitmaps.** gb.bp has a bitmap format and the store has tombstone bitmaps at word granularity (LANG-DB §9). 2206.01149 (rank/select at "~3.51 %" space overhead, O(1)), 2009.12809 (rank/select over MUTABLE bitmaps with `flip(i)`), 2605.25528 (the same engineered on ARM64: "1.4x speedup in rank queries through asymmetric 4096/256-bit block boundaries", abstract). A rank index over the mask makes "bitmap position -> dense index" O(1), which the bitmap-to-CSR conversions in gen_gb pay with a popcount scan today. ~80 lines, `cnt`+`addv` on NEON or scalar popcount; only worth it if a profile shows the conversion.
- **Eytzinger layout for any sorted-key binary search.** 1509.05053: for large n "the Eytzinger layout is usually the fastest" (abstract). If the PK bucket index ever falls back to a binary search over sorted keys, this is the layout; the T100 grid index does not search, so today: nothing.
- **Hardware memory tagging (MTE) as C1's zero-word alternative.** 1802.09517 describes AArch64 memory tagging; `grep mte /proc/cpuinfo` on this box: absent. Not available here; a target phone with MTE would make C1's bounds checks partly a `prctl`, still zero dependencies. Note for C1's card.
- **Group commit needs no tuning knob.** 2606.18187 (2026, abstract): in closed-loop OLTP "flush the instant the device is free" is "within about 0.1 % of the best oracle-tuned timer at every load". B1's `st_commit_batch` should therefore not grow a timer. Helps a row; stated once and left to the other analyst.
- **A binary sparse-matrix interchange format exists.** 2506.19175 "Binsparse": a cross-platform binary CSR/COO spec. Not a dependency (a layout), useful only if a store ever needs to exchange a matrix with SuiteSparse for an oracle at scale; python oracles cover that today.
- **Deterministic whole-binary translation** (2605.08419) and machine-code bounded model checking (2507.09539 "rotor/bitme", RISC-V) are the two corpus items that reason about MACHINE CODE rather than an IR -- the only verification shape that could ever apply to a compiler with no IR. Both are early; neither targets AArch64 in its abstract. Watch, do not build.

## 11. What could not be determined from abstracts

- Whether any MLP paper's gain survives on a phone-class core with a smaller miss queue than a server Xeon: every abstract in §3 measured on x86 servers except 1701.05478 (big.LITTLE, but DAE not group prefetch). Only the kill experiment answers it.
- The magnitude of reordering wins on graphs with W's shape (bipartite order-courier-merchant, time-ordered ids); the abstracts report social/web graphs.
- Which of the CSR-build phases carried the 17.3 s (§5.2 lists three candidates in the literature's order; the profile program prints the table and it was not run into the tree).
- Whether TPDE's "on par with LLVM -O0" is measured against -O2 anywhere in its body; the abstract does not say and the 2-3x figure used in §5.1 is outside knowledge, marked as such.
- Whether 2502.13862's "76x on loading" compares like with like (SuiteSparse builds a full CSR; their structure may not); the abstract gives ratios without the representation.
- The decode-throughput law's T_dec for a scalar bebop decoder: the paper's ~2 values/cycle is portable C; §7.3's 1.4x adjustment is the project's own codegen gap applied by analogy.
- Anything about citation weight, adoption or follow-up of any paper: the corpus has no such signal, by construction.
