## 1. Wall: the 1.37x codegen gap at equal algorithm

The literature study's verdict was "one-pass codegen has no more gate to give". Every idea here accepts that WORDS are done and attacks something that is not words.

### 1.1 Is the residual even codegen? A twin that separates words from load-branch coupling -- `PLAUSIBLE` [inversion: negate "the gap is instruction count"]

**Mechanism.** 2608.11380 ("The Fallacy of Independent Ceilings", abstract): in irregular loops, hard-to-predict branches and cache-missing loads in the same loop are NOT independent -- "better branch prediction leaves more long-latency loads in the out-of-order window", and 40 % of their kernels beat the product of the two isolated ceilings by > 6 %. The join twin's probe loop has a data-dependent branch (row-length test) and three dependent loads. If `rustc -O`'s loop mispredicts less often (different loop rotation, `tst` vs `cmp #1`), each avoided mispredict also un-squashes the loads that were in flight -- the 1.37x would then be a coupling artefact, not 4 extra words. **What would have to be true.** The gap must change when the branch becomes perfectly predictable. **Cheapest test.** Run the existing join twin (both compilers, unchanged) on a sorted-key input (row lengths monotone, branch predictable) and on the Zipf input; if bebop/Rust drops from 1.37x toward 1.1x on sorted keys, the residual is coupling and the lever is in the loop SHAPE (2.2 below), not in the emitter. Zero code change; one slot run.

### 1.2 Loop-head alignment: the one codegen lever that is not a word -- `LONG SHOT` [inversion: "the words are right, the addresses are wrong"]

**Mechanism.** The emitter lays fns out contiguously (`em()` appends words; there is no alignment anywhere: `grep -n align bebop.bp` finds only comments). A loop head that straddles a 32-byte fetch block, or a 64-byte line, costs a fetch bubble per iteration on cores whose front end fetches aligned blocks; on Intel this is the classic DSB effect, on the A78 (MOP cache, 32 B fetch) it is smaller but nonzero and nobody here has measured it. **What would have to be true.** K8H's inner loop must currently sit at an unlucky offset, and a 1.1x row must be sensitive to 1-2 fetch bubbles per iteration (it is: 8-12 words per iteration). **Cheapest test.** Compile K8H, then pad the fn preamble with 0..7 `nop` words by hand (a one-line `em(insns, n, 0xd503201f)` loop behind an env var) and plot ms against the loop-head offset mod 32. If the curve is flat, the idea is dead in 30 minutes; if it is not, the emitter gains an "align loop heads to 32 B" rule (~10 words, no IR, byte-exact fixpoint still holds because the rule is deterministic).

### 1.3 The emission lottery: compile slower on purpose, because the compiler runs in microseconds -- `LONG SHOT` [constraint as asset: 157 KB compiler callable at runtime; inversion: "the compiler is fast" negated]

**Mechanism.** The register model makes tie-break decisions (which operand goes in which register, commutative operand order, `cmp #1` vs `tst`, loop rotation) deterministically. Give `par_compile` a 64-bit seed that perturbs only those tie-breaks; PreJIT compiles a kernel K times (a kernel fn compiles in microseconds -- the whole 6,909-line compiler compiles in 2.15 s), runs each variant once on a 1 ms slice of the REAL input, keeps the fastest words in `.gbpool` keyed by (source hash, compiler digest, seed). This is 1211.0557's STOKE idea (stochastic search over instruction sequences; abstract: matches or beats `gcc -O3` from `-O0` binaries) with the search space cut down to what a one-pass emitter can vary and correctness kept BY CONSTRUCTION (every variant is a legitimate emission of the same source; no equivalence checking needed, unlike STOKE). It is not the refuted "race several JIT'd plans": trials are sequential micro-runs of one loop, not concurrent memory-bound kernels. **What would have to be true.** The emitter's tie-breaks must span the distance between bebop's 12-word and rustc's 8-word loop. The A2b closure said the last residual was "one `cmp #1` vs `tst`" -- so the space might be two or three variants, not a hundred. **Cheapest test.** Before writing any code, enumerate by hand the tie-break sites in `vs_binop_reg`/`vs_try_*`/`emit_cond` that affect K8H's loop and count distinct emissions reachable; if fewer than ~8, the lottery has nothing to draw from and dies on paper. If more, the seed is ~30 words of compiler and the trial harness lives in gen_gb.

### 1.4 `word(imm)`: the zero-dependency inline assembler that one ISA makes possible -- `PLAUSIBLE`, with a manifesto tension [constraint as asset: one ISA only]

**Mechanism.** Because bebop targets exactly one ISA and emits raw words, a builtin `word(0xXXXXXXXX)` that appends one literal instruction is ~20 lines (`em(insns, n, literal)`) and gives kernel authors the whole A78 at the cost of zero IR and zero dependency. The 12 gen_gb templates could carry hand-tuned inner loops as literal words; `crc32x`/`hvham` were added as builtins for exactly this reason, one at a time. **What would have to be true.** The honesty floor must accept a fn whose body bpref cannot interpret: `tools/bpref.py` would raise on `word`, so the oracle for a `word`-bearing kernel is the unspecialised kernel (same fold, same input), which the pool ABI already requires for every generated kernel. The register model must be told which registers a `word` block clobbers (a second argument: a clobber mask) or it will keep a live value in x3 across a hand-written `ldr x3`. **Cheapest test.** Take the K8H loop words from `rustc -O`'s objdump, place them in a bebop fn via a scratch `word` builtin with the loop-carried values pinned to the registers the model assigns, and measure: if the row goes from 1.1x to 1.0x the mechanism works and the question is only whether the operator wants it (it lets a kernel author bypass the compiler, which is what C1's kernel dialect exists to prevent -- so `word` would be forbidden inside `kernel fn`).

### 1.5 Stencils harvested from the twin: copy-and-patch where the templates come from `rustc -O`, not from LLVM -O0 -- `LONG SHOT`, probably against the spirit of "single compiler" [cross-domain: copy-and-patch]

**Mechanism.** The literature study filed copy-and-patch (2011.13127) under "LLVM -O0 class" because its stencils are compiled by clang at build time from generic C. Invert the provenance: the tree ALREADY builds an honest `rustc -O` twin of every kernel; harvest the twin's inner-loop bytes at development time (a dev tool, like python for bpref), check them in as a words table with the twin's source as their oracle, and let gen_gb patch operands (base register, bounds) into copies. The 1.37x vanishes for the 12 template kernels by definition, because the loop IS the twin's loop. **What would have to be true.** The stencil's register use must be reconcilable with the arena registers (x17, x27/x28 for the capacity trap) -- a fixed-up copy, not a raw paste -- and the operator must accept machine words whose origin is a second compiler inside `bebop.bin`. That is the tension: no C anywhere in the toolchain is kept to the letter (rustc is not C) and broken in spirit (a second code generator's output ships). **Cheapest test.** The same experiment as 1.4, which decides the mechanism; the decision is then political, and this document does not make it.

### 1.6 Superoptimisation with testing as verification -- `PROBABLY NONSENSE, BUT`

**Mechanism.** Run STOKE-style MCMC over the 12-word loop at PreJIT time, scoring candidates by the fuzz oracle on random inputs rather than by a proof (bebop has no IR to prove against). **Why it is nonsense here.** A candidate that passes 10^6 random inputs and fails on the 10^6+1st is a miscompile in code that moves money; the honesty floor (TG-DONE 4: zero tolerated miscompiles) forbids it and should. **But** the thought points somewhere real: the tree already tolerates SAMPLED verification for data (B4's gate: "folds == oracle every 10^4"), and 1.3 gets STOKE's search without STOKE's soundness problem because every candidate is an honest emission. 1.6 is the wrong way to get 1.3.

## 2. Wall: latency-bound traversal (23-45 ns per edge slot against a 0.67 ns floor)

The careful answer is prefetch (D2) and relabelling (D3). Everything here is a different lever.

### 2.1 The i64 cell IS a 64-lane SIMD register for boolean semirings: multi-source BFS as A x F over (OR, AND) -- `PLAUSIBLE` [constraint as asset: every cell is exactly 8 bytes]

**Mechanism.** The G8 row is "BFS, 100 sources": 100 separate traversals, each paying the full latency-bound gather. Take 64 sources at once: the frontier is not a bitmap over vertices but ONE i64 per vertex whose bit s is "vertex reached from source s at this level". The push step becomes `nx[u] |= fr[v]` (an OR of one cell into one cell per edge slot), the semiring is (OR, AND), and 64 BFSs share every `rp[v]`/`ci[k]` miss. In GraphBLAS terms it is SpMM with a 64-column boolean matrix packed into the cell -- 2408.11988 (abstract) names "multi-source breadth-first search" as the first application of tall-skinny SpGEMM; the non-arXiv original is Then et al.'s MS-BFS (VLDB 2015), absent from this corpus by construction. `gen_gb.bp` already generates per-(op, semiring) kernels, so this is one more semiring instance plus a frontier test `fr[v] != 0`. **What would have to be true.** The workload must ask for many sources (G8 does; W's order-log queries may not -- "reachable from THIS order" is one source, and then 2.1 buys nothing). The 8 MB `fr`/`nx` (i64 per vertex, no longer 128 KB bitmaps) must not turn L2 hits into misses faster than the 64x amortisation pays -- at 64 sources per pass the gather budget per source drops from 23 ns to under 1 ns per slot even if every cell access misses. **Cheapest test.** `gbfs_push` with `fr`/`nx`/`vis` as `[i64]` cells instead of bitmaps and `|=` instead of `setbit`, 64 sources, one slot run; gate to beat: 64 x today's 45 ns/slot in one pass, i.e. the pass may take up to 2.9 us per slot before it loses. The prediction is under 0.1 us per slot.

### 2.2 Always write, subtract later: a branchless push step by deferring the visited mask -- `PLAUSIBLE` [inversion: "being wrong per slot is acceptable and cheap to fix per level"]

**Mechanism.** Today's generated push loop (`selfhost/std/gen_gb.bp:245-269`) does, per slot: read `vis` bit, `take = 1 - bit`, `if take then setbit(vis)`, `if take then setbit(nx)`, `cnt += take`. The two `if` arms are stores, so they are branches, not csels (A2's csel covers pure arms), and their outcome is data-dependent -- exactly the coupled load-branch loop of 1.1 and of 1411.1460 (abstract: mispredictions cost BFS/CC 30-50 %). Invert it: per slot do ONLY `nx[word(u)] |= bit(u)` -- unconditional, no read of `vis`, no branch, no counter. After the level: `nx &= ~vis; vis |= nx; cnt = popcount(nx)` -- three passes over 128 KB bitmaps at ~12 GB/s, ~30 us per level. This is the GraphBLAS structural-complement mask applied AFTER the product instead of inside it. The inner loop becomes `ldr ci; lsr; ldr word; orr; str; add; cmp; b` -- one load stream (ci, sequential), one L2-resident read-modify-write, zero data-dependent branches. **What would have to be true.** `nx` must stay cache-resident (128 KB at n = 1M; the A78 L2 is 256 or 512 KB on this SoC and sysfs hides which -- probe 0.2), and the duplicate writes to already-visited vertices must be cheaper than the branches they replace (they are L2 hits; the branches were mispredicts that squash in-flight ci loads). **Cheapest test.** Twelve lines in `gbfs_push` plus the three bitmap passes; same fold, one slot run; prediction: push-step ns/slot at least halves. If it does not, the row-start misses (`rp[v]`, first line of the row: one per frontier vertex, ~10 slots) dominate and D2's prefetch is the only lever left.

### 2.3 Cores DO scale for gathers: B6's 12 GB/s stop rule uses the wrong ceiling -- `PLAUSIBLE`, cousin of B6 and of the literature study's §10 [inversion: negate "one core saturates DRAM"]

**Mechanism.** "One A78 saturates DRAM at 12 GB/s, and so do three" is a SEQUENTIAL fact; a latency-bound gather moves 64 B lines at ~10-20 outstanding misses per core (LANG-DB §9's own estimate), so its effective bandwidth is ~2-4 GB/s per core and the ceiling that binds is misses-in-flight, which is per core and adds up across cores -- including the four A55s, whose smaller miss capacity is still nonzero and whose use in the study (§10) was as prefetch helpers, not as gatherers. **What would have to be true.** The traversal must be partitionable by frontier word (it is: `gbfs_push` iterates `w < nw`), and the box's memory controller must not serialise random lines from different cores (unknown). **Cheapest test.** `sgraph2` frontier BFS with the frontier-word range split across 1 / 3 A78 / 3 A78 + 4 A55 via the existing `sys_clone`/`sys_setaffinity` builtins, bitmap merge by OR at the end of each level; if 3 cores give < 1.5x the random-access ceiling is shared and B6's rule stands; if they give ~3x, B6's stop rule needs a second ceiling ("random GB/s") and the A55s are gatherers, not helpers. Step 0 of B6 (do clone threads count against the 32-process cap) is a prerequisite either way.

### 2.4 Buy cache lines with bytes: pad every CSR row to a 64-byte boundary -- `LONG SHOT` [inversion: "the store is smaller on purpose" negated]

**Mechanism.** At average degree 10 and 8 B slots a row is 80 B and straddles two lines; a frontier vertex therefore costs two random misses (rp[v] a third). With A8's u32 a row is 40 B and straddles a line half the time; padding rows so none straddles (cost: up to +37 % ci bytes at degree 10, and rp still indexes slots) makes it one miss per row. This trades the size row (already lost 2.5x) for the latency row. **What would have to be true.** Misses per frontier vertex, not bytes streamed, must bind (2.2's own kill test says which), and the padding must not push `ci` past a TLB reach cliff (4 KB pages, THP never). **Cheapest test.** Generator-side: emit `ci` with per-row padding in `sgraph2`'s build, same fold, same 100 sources; ns/slot before/after in one run. Note the interaction with D3/D4: after relabelling, 16-bit deltas fit ~4 rows per line and padding becomes pointless -- 2.4 is only worth testing BEFORE those exist.

### 2.5 Compile the graph into code: `ci` as immediate operands -- `PROBABLY NONSENSE, BUT` [inversion: "the graph is never materialised as data"; constraint as asset: compiler at runtime]

**Mechanism.** The gather `x[ci[k]]` is latency-bound because the address of the second load depends on the first. If each edge were emitted as `movz/movk x1, #dst; ldr x0, [x17, x1, lsl #3]`, the address is an immediate: no dependent load, the front end can issue every gather as soon as it is decoded, and the instruction stream is sequential, which the I-side prefetcher handles as well as the D-side handles ci. The compiler runs in-process, so a CSR VERSION becomes a code image. **Why it is probably nonsense.** 12-16 B of code per edge against 8 B (4 B after A8) of ci -- the I-cache misses replace the D-cache misses byte for byte, plus the miss-capacity limit that binds is the same MSHR pool either way, which is exactly what D2's `prfm` reaches at 8 B per edge without any code. 10M edges become 160 MB of text per version. **But** the thought isolates the real variable: whether dependent-address loads or miss capacity is the binding term. The cheap test is 2.2 plus D2, not this; and if a graph is TINY and hot (the 12x12 FSM matrix of B8), compiling it to code is exactly right and gen_gb should do it -- the semiring kernel over a 144-entry matrix should be 144 immediates, not a loop over a store object.

### 2.6 Scale inversion, for the record [scale inversion]

At 1000x smaller (10K edges) everything is in L1 and the 1.37x codegen gap becomes the whole traversal gap -- so the cheapest way to measure the emitter's true cost on graph code is a graph that fits in L1, which no bench script uses. At 1000x larger (10G edges, 80 GB, the phone's flash) the store cannot be resident, every gather is a flash read, and the external-memory literature (0802.2847, abstract: static BFS is Omega(n / B^{1/2} + sort(n)) I/Os on sparse graphs) says the ONLY viable BFS is the level-synchronous, sorted-frontier, batched form -- i.e. the semiring SpMSpV, not the queue. The thesis "traversal IS matrix-vector product" is more right at the scale the box cannot reach than at the scale it can; it is worth knowing which regime a G8 number is arguing about.

## 3. Wall: the persistence tax (MAP_SHARED 27,404 ms vs MAP_PRIVATE 1,239 ms, one flag)

D1 says "build in RAM, publish sequentially" for the CSR build. The ideas here ask what the 22x MEANS and whether the file should ever be writable at all.

### 3.1 The file is never mapped writable: MAP_PRIVATE view + `pwrite` of the contiguous tail -- `PLAUSIBLE` [inversion: "the file IS the memory image" kept for reads, negated for writes]

**Mechanism.** The arena is append-only and objects are immutable after commit (LANG-DB §0.6, §0.8: no free lists, CoW versions, `prev` edges). Therefore, within a transaction, every byte that will ever be published lies in `[old_tail, new_tail)` -- the dirty set is CONTIGUOUS BY CONSTRUCTION, and the kernel's per-page dirty tracking (the thing R1 measured at 22x) is tracking something the store already knows. So: map the file MAP_PRIVATE (flags 2, already used by `st_compact` at `store.bp:357`) for the whole life of the process; `st_alloc` hands out addresses in the private view; `st_commit` does one `pwrite(fd, tail_range)` (syscall 68, not yet a builtin: `sys_write` exists, `pwrite64` is one word), `fsync`, then `pwrite` of the superblock toggle -- the same two-superblock protocol, minus msync, minus a writable shared mapping. The R1 penalty disappears for EVERY program's scatter, not only for CSR builds (the literature study's worry that a file-backed arena "would put every `zeros` scatter on the 24x path" is answered by never having a shared writable mapping). Private pages written since the last remap are anonymous copies; after the commit's `pwrite` they duplicate page-cache pages until the range is remapped (one `mmap MAP_FIXED` over the published range, ~microseconds), which also makes readers in other processes see the same bytes. LMDB's default (no `MDB_WRITEMAP`: writes via `pwrite`, reads via a read-only map) is this design and it is the design the 2026-09-04 critique's option D-H(1) sketched ("MAP_PRIVATE staging view ... published by pwrite/msync of the dirty range") before R1 existed; what is new is that R1 now gives it a 22x reason and the append-only invariant removes the "dirty range" tracking the critique still assumed. **What would have to be true.** No committed object may be mutated in place. Today that is nearly true and not quite: edge tombstones are bitmaps ("tombstone 10 % + commit", G8 row) and B4's blocktab CoW must never flip a bit in an old block; every in-place exception needs 3.2 or 3.3, or a rule that makes it an append. And `pwrite` under proot costs ~10-30 us per syscall (docs/RESEARCH-DEPS-2026-09-06.md, table row 6) -- one per commit, against today's msync at ~100 us per page-range. **Cheapest test.** The R1 driver with the store arm mapped flags = 2 and the commit replaced by `sys_write` of the tail range from an fd opened O_APPEND (no new builtin needed for the experiment); predicted: within 1.3x of the 1,239 ms MAP_PRIVATE number, fold identical, file byte-identical to today's. One slot run.

### 3.2 Soft-dirty bits: user-space page dirty tracking for the in-place exceptions, verified available here -- `LONG SHOT` [cross-domain: checkpoint/restart tools' mechanism, CRIU-style]

**Mechanism.** Linux's soft-dirty facility (`echo 4 > /proc/self/clear_refs`, then bit 55 of each `/proc/self/pagemap` entry) marks pages written since the last clear -- the kernel's write-protect-once-per-page mechanism, but on the PROCESS's terms: one protection fault per page per COMMIT (~3.5 us x pages touched) instead of whatever MAP_SHARED does per store. Probed today: both files are accessible from this proot (0.2). At commit, read the pagemap for the mapping (8 B per page; 80 MB = 156 KB of pagemap), `pwrite` the soft-dirty pages, clear. This is what 3.1 needs for tombstone bits and any other in-place write. **What would have to be true.** The kernel must be built with `CONFIG_MEM_SOFT_DIRTY` -- the write to `clear_refs` succeeding does NOT prove the bits are set (the write is accepted regardless); and proot must not interpose `/proc/self` in a way that returns another process's map (it translates paths; `/proc/self` resolves in the kernel). **Cheapest test.** Ten lines of python: mmap 16 pages MAP_PRIVATE, clear, write page 3 and 9, read pagemap, check bit 55 is set on exactly those two. Under a minute; if the bits are never set, 3.2 is dead and 3.3 is the fallback.

### 3.3 Hash-diff publishing: the store's own `crc32x` as dirty tracking -- `LONG SHOT` [cross-domain: rsync's rolling-checksum publish]

**Mechanism.** If 3.2's bits are absent, dirty pages can be FOUND instead of TRACKED: keep a per-page crc table of the file image (4 B per page: 80 KB for 80 MB), at commit recompute `crc32x` over every page of the private view (hardware CRC32X at 8 B per step, `bebop.bp:1444`; 80 MB in ~10-20 ms) and `pwrite` the pages whose crc changed. Cost is O(mapping) per commit regardless of how little changed, which is fine at 80 MB and wrong at 2 GB -- which is why 3.1's contiguous tail is the primary mechanism and this is only for the in-place exceptions, over the object ranges the store knows are mutable (tombstone bitmaps), not over the whole file. **What would have to be true.** The mutable set must be enumerable (it is: the layout table knows which objects are bitmaps). **Cheapest test.** None needed beyond 3.2's outcome; the crc loop already exists.

### 3.4 The 22x might be reclaim, not tracking: the zram hypothesis, and a 64 MB `mlock` to test it -- `LONG SHOT` [inversion: negate the accepted diagnosis]

**Mechanism.** R1's inversion result is odd on its face: a tmpfs-backed MAP_SHARED store was 3x SLOWER than f2fs (36.5x vs 12.8x). Dirty-page tracking should not care about the backing store; RECLAIM does. This box runs with 1.9-2.5 GB of zram swap in use at idle; under memory pressure the LRU cleans and unmaps shared file pages continually, and a tmpfs page that is reclaimed goes to zram (compress on the way out, decompress on the way back in -- 2502.12826, abstract, is the phone-side literature on exactly this cost), while an f2fs page is written back to flash and re-read. A random scatter over an 80 MB working set that keeps being unmapped would show precisely "1.8 us per store, proportional to stores not pages", and would explain why tmpfs is worse. Anonymous MAP_PRIVATE pages are also reclaimable, but the LRU treats them differently and they were fast -- consistent, not proof. **What would have to be true.** `/proc/vmstat`'s `pgsteal_*`, `pswpout`, `nr_vmscan_write` must move during the MAP_SHARED run and not during the MAP_PRIVATE run (readable unprivileged; `/proc/sys/vm/*` is not). **Cheapest test.** Two runs of the existing driver bracketed by `cat /proc/vmstat`; if the counters move, `mlock` the working set -- `RLIMIT_MEMLOCK` is 64 MB here (probe 0.2), enough for `rp` plus the bitmaps, and `sys_mlock` is one syscall word -- and re-run; if the 22x collapses under mlock, the tax is reclaim and 5.3 becomes a first-class store rule ("pin the hot 64 MB"). If the counters do not move, this idea is dead in ten minutes and the accepted diagnosis stands.

### 3.5 Footnote: `zeros()` zeroes memory the kernel just zeroed -- `PLAUSIBLE`, tiny

`emit_zeros` (`bebop.bp:5893-5904`) stores `xzr` over the whole allocation because the bump cursor is reset per `call_jit` and re-allocations must not see stale cells. For a FRESH mapping the pages are already zero; a high-water mark on the arena cursor ("never touched above here") would skip the loop for first-time allocations, which is every large allocation in a CSR build: 80 MB of stores and 19,500 first-touch faults moved from the memset to the fill loop (where they happen anyway). Worth ~5-10 % of the 747 ms plain-array build, measurable by deleting the six words behind an env var. The DC ZVA item (T75) was deleted for the right reason; this is not that -- it is not zeroing faster, it is not zeroing.

## 4. Wall: size (2.5x loss to sqlite)

### 4.1 The compiler is the decompressor: per-column JIT decoders with the column's statistics as immediates -- `PLAUSIBLE` [constraint as asset: compiler at runtime]

**Mechanism.** The corpus study held D4 (sub-32-bit indices) back because a SCALAR bit-unpacker is decode-bound below ~20 bits: a generic decoder loads a width from a variable, shifts by a register, masks by a register. But bebop can compile a decoder PER COLUMN at `st_open` or at compaction: the bit width, the frame-of-reference base, the delta stride and the dictionary head are then IMMEDIATES (`ubfx x0, x1, #lo, #w` unpacks one field in one word; four 16-bit fields from one 64-bit load are one `ldr` and four `ubfx`), and a `.gbpool` entry keyed by (column layout digest, compiler digest) caches it. At 4-wide issue that is ~1.25 cycles per 4 values -- above 3 values per cycle, which moves the decode ridge below 16 bits with no NEON and no A9 dependency. This is the "specialise the code to the data" family (partial evaluation of the decoder), and it costs the compiler nothing: gen_gb already generates per-(op, semiring) kernels; this is per-(op, semiring, encoding). **What would have to be true.** Column statistics must be stable between compactions (they are: the store is append-only and compaction is when layouts change), and the decoder's I-cache footprint must stay small (one fn per column, ~50 words). **Cheapest test.** Hand-write the `ubfx` unpacker for a 16-bit `ci` as a bebop fn with literal shifts (no compiler change), run the frontier BFS on 16-bit `ci` vs u32 -- the D4 gate as written (ns/slot not above u32's) with bytes/slot = 2. If scalar `ubfx` code holds the ns/slot line, D4 loses its NEON dependency.

### 4.2 Indexes are cache: count only the log -- `PROBABLY NONSENSE, BUT`

**Mechanism.** The CSR, the bucket index and the grid index are all DERIVED from the object log; store only the log and rebuild derived objects at open (the in-RAM CSR build is now ~1.2 s per 10M edges). The size row would then compare the log against sqlite's table PLUS its indexes, which is what sqlite's 34 MB already includes. **Why it is nonsense.** It is a redefinition, not a mechanism; "instant start" is a mandatory property (ROADMAP Phase B header) and a 1.2 s rebuild at open is the opposite; sqlite would win any honest restatement. **But** it points at a real asymmetry the size gate does not separate: how much of the 85 MB is ENTROPY (records) and how much is DERIVED (indexes, i64 padding of small values). A size row split into "log bytes / derived bytes / padding bytes" would say whether C2's header amortisation or D4's narrow cells is the lever, before either is built; today the row cannot say.

### 4.3 Kolmogorov: the benchmark graph is a program -- `PROBABLY NONSENSE, BUT`

The G8 graph is generated by a `.bp` program (an LCG over 2E slots, `sgraph2.bp:7`); the smallest store that represents it is the generator and its seed, a few hundred bytes, and "materialise at open" is again 1.2 s. Nonsense for real data. **But** it is the honest reading of every synthetic benchmark's size row: a synthetic graph has almost no entropy, so any compression scheme (4.1, D4, f2fs-level) will look better on it than on W's order log. The size gate should carry a real-data row before any compression lever is credited.

## 5. Wall: the phone's own limits

### 5.1 The counters are hidden by `security.perf_harden=1`, not by `perf_event_paranoid` -- `LONG SHOT`, operator lever [inversion: "the box has no counters" negated]

**Mechanism.** ROADMAP C5 calls the `swpmu.bp` EACCES stale because `perf_event_paranoid` reads -1. Probed today: `getprop security.perf_harden` = **1** (0.2). On Android, that property makes the platform deny `perf_event_open` to untrusted apps by SELinux policy, independently of the paranoid sysctl, and it is the property simpleperf's own documentation tells developers to clear: `adb shell setprop security.perf_harden 0` (needs a PC and USB debugging; does not survive a reboot). With counters, 1.1, 2.2 and 3.4 become one-run diagnoses (`br_mis_pred`, `l2d_cache_refill`, `mem_access` per slot) instead of A/B inferences, and the box's 25 % wall-clock drift stops mattering for RATIOS because cycle counts are frequency-invariant. **What would have to be true.** Termux's SELinux domain must be the one the property gates (it is `untrusted_app_27`, BOX.md), and proot must pass syscall 241 through unchanged. **Cheapest test.** After the setprop, the existing `swpmu.bp:1-4` probe; five minutes of the operator's time, zero code.

### 5.2 The durable-commit row is a proot row: measure the store outside the proot -- `PLAUSIBLE` [inversion: "the box is proot" negated]

**Mechanism.** Under proot every syscall is a ptrace round trip (docs/RESEARCH-DEPS-2026-09-06.md, table row 6, estimates 10-30 us; LANG-DB §0.4 measured `rename` at ~270 us and one-page `msync` at ~100 us). The only store row that LOSES to sqlite on speed is durable commit: 506 us against WAL NORMAL's 78 us (0.15x) -- and sqlite's number was taken via python's ctypes, i.e. also under proot, but a WAL commit is one `write` + one `fdatasync` where the store's is msync + msync + superblock; the loss may be entirely the extra ptrace stops. `bebop.bin` is a static binary with no libc that runs on Android's own syscall ABI (docs/ANDROID.md: "no emulation layer"; the `execmem` denial is fixed), so it can run in plain Termux with no proot at all; only the Ubuntu userland needs proot. **What would have to be true.** Termux's seccomp/SELinux must permit the store's syscalls from an app domain (mmap MAP_SHARED of a file in app storage, msync, fsync, rename, clone -- all ordinary), and the f2fs path must be app-accessible (it is `/data/data/com.termux/...`). **Cheapest test.** Copy `bebop.bin`, the seed loader and `sbench`'s store program to Termux's home, run the commit row there, compare 506 us. If it drops toward the 100 us the two msyncs cost by themselves, the 0.15x row is a harness artefact and the honest comparison is both engines outside proot; if it does not, the tax is real and 3.1's single `pwrite` per commit is the lever. Twenty minutes, no code.

### 5.3 Pin the hot 64 MB -- `LONG SHOT`, conditional on 3.4

`RLIMIT_MEMLOCK` is 64 MB here (0.2), which is unusual (glibc systems default to 8 MB) and enough for `rp` (8 MB at n = 1M) plus every bitmap plus the L0 log. If 3.4 shows reclaim in the 22x, `mlock` of the store's hot objects at open is a one-word builtin and a rule in `st_open`; if 3.4 shows nothing, this is dead with it.

### 5.4 What was NOT proposed here

Threads versus the 32-process cap (B6 step 0 owns it); A55s as prefetch helpers (§10 of the literature study); anything needing a GPU, NPU, DSP or `io_uring` (no API from this domain).

## 6. Walls nobody has named

### 6.1 The oracle is the bottleneck: N-version fuzzing by randomised emission, no python in the loop -- `PLAUSIBLE` [constraint as asset: the compiler is deterministic and cheap]

**Mechanism.** The fuzz rate is 1.5-3.5 programs per second because every seed runs `bpref.py` in a forked CPython (`bench/fuzz/fuzz_batch.py:4-6`: interpreter start was 70 % of a seed before the fork trick). TG-DONE 8 wants 10^5 seeds per promoted binary: 8-18 hours per binary at that rate. 1.3's seed already exists as a concept: compile every fuzz program TWICE with different tie-break seeds (register assignment order, operand order), run both native images (microseconds each), compare outputs; disagreement = a miscompile in at least one emission, found with no interpreter. This is N-version / metamorphic compiler testing with the compiler's own nondeterminism as the second version; DIVERGE-42122 (a 9th-parameter spill clobber) is exactly the class a different register order exposes. bpref stays as the arbiter for disagreements and as the nightly ground truth. **What would have to be true.** The two emissions must differ enough to disagree on real bugs (a bug in the parser is shared by both and stays invisible -- this finds register-model and emission bugs only), and the seed must be plumbed without touching the fixpoint (seed 0 = today's emission, byte-exact). **Cheapest test.** Take the 32 DIVERGE repros from A4's rounds, compile each with two hand-chosen operand orders (a scratch env var in `vs_binop_reg`), and count how many of the 32 the pair would have caught without bpref. If fewer than a third, the second version is too similar and the idea dies.

### 6.2 Provenance for free: the same kernels over a provenance semiring -- `LONG SHOT` [cross-domain: provenance semirings from databases into the tensor engine]

**Mechanism.** MANIFESTO C3 makes auditability the law; gen_gb generates kernels per (op, semiring). Provenance semirings (the K-relations line; 2511.09203, abstract: "the choice of semiring determines the notion of provenance", Boolean algebra gives which-inputs dependency) say that running the SAME query over a different semiring yields its derivation instead of its value. Instantiate gen_gb with values = i64 bitsets over 64 tagged inputs (OR, AND): the result of a join or a reachability query then carries, in every output cell, WHICH of 64 source events contributed -- the "why" of an order's state, computed by the identical kernel text at identical speed (it is 2.1's semiring). Beyond 64 inputs the value becomes a `ref` to a lineage list in the arena, and the semiring is (union-by-append, concat), which is slower but still one kernel. **What would have to be true.** W's audit questions must be answerable as "which events reached this cell" rather than "in what order" (order needs the tropical semiring on timestamps, also one instance). **Cheapest test.** One gen_gb instance (OR, AND) over a 64-tagged toy graph, fold checked against a python why-provenance oracle; an hour, no compiler change.

### 6.3 Canonical compaction: a byte-identical store image as a state hash for the mesh -- `LONG SHOT` [constraint as asset: the project already lives by byte-exact fixpoints]

**Mechanism.** Cheney compaction copies the live graph in traversal order from the root (`store.bp:355-416`); if the traversal order is deterministic in the LOGICAL state (root, object graph, and a tie-break that does not depend on allocation history), two nodes holding the same logical state produce byte-identical compacted files, and `crc32x` of the file is a state digest -- the data-side twin of `gen3 == gen4`. Delta-state CRDTs (1603.01529, 1410.2803; abstracts: anti-entropy by shipping join-decomposition deltas) and digest-driven sync (2505.01144, abstract: 18x less transfer than full-state sync) then apply directly: the per-object crc the store already keeps is the digest, and the append-only tail is the delta. DECISIONS D0 says "decentralized, local-first, mesh"; the store has no sync story yet. **What would have to be true.** Cheney order must not depend on insertion order -- it does today (objects are visited in `ref` order, and a record's `ref`s point at objects allocated in arrival order), so canonical form needs a sort key (object digest) at compaction, which costs a sort of the live set per compaction. **Cheapest test.** Build the same 10^4-record state in two insertion orders, compact both, `cmp` the files; they will differ today, and the diff says how far from canonical the layout is.

### 6.4 Code in the store: orthogonal persistence, and why A10's memo is C3's commit chain -- `PROBABLY NONSENSE, BUT`

**Mechanism.** 1006.3448 ("Orthogonal Persistence Revisited", abstract): treat objects uniformly regardless of longevity or type -- a Smalltalk/Lisp image. Since a fn compiles to a contiguous word block and `bl` targets are a layout table, A10's per-fn memo IS a store: fn = object keyed by hash(text, facts), layout table = index, a self-compile = a transaction, "one-fn edit in 0.3 s" = append one object and swap the root, and time-travel of CODE comes free from `prev`. **Why it is nonsense here.** LANG-DB §0.7 forbids loading code from the data file, for a reason (a tampered store must not run), and the `.gbpool` defect (B3: kernels from one compiler dispatched by another) is the small version of the catastrophe. **But** the memo cache (`.becache`, `.gbpool`) is a store in every respect except that it was written twice by hand; if C3's commit-object chain lands, A10 should reuse it rather than grow a third cache format -- and `compiler_digest` in the key is the same discipline as the migration table's sha256 names.

## 7. The three I would test first, and why

1. **3.1 + 3.4 together, one slot run each (persistence).** 3.1 is the highest expected value in this file: it turns D1 from a per-structure discipline into a property of the store, removes the only writable shared mapping the process ever holds, and its test is the R1 driver with one flag and one syscall changed. 3.4 rides along for free (two `cat /proc/vmstat`) and, if it fires, changes the DIAGNOSIS that D1 rests on -- which would be the most surprising result on this box this week.
2. **2.2 (branchless push, subtract later).** Twelve lines in one generated kernel, same fold, a prediction that is either right by 2x or wrong by nothing; and its outcome tells D2's owner whether misses-per-frontier-vertex or per-slot branches were the binding term before any `prfm` word is added. 1.1's sorted-key twin is its zero-code cousin and should run in the same slot.
3. **2.1 (64-source BFS in one i64 cell).** The G8 row as written (100 sources) is the workload it was made for; the mechanism is one semiring instance in a generator that already exists; and if it works it is the first place where "every cell is 8 bytes" is a measured advantage rather than a measured 2.5x cost.

5.1 (one `setprop`) and 5.2 (run the commit row outside proot) are not in the three only because they are the operator's minutes, not a slot's -- they should happen first anyway.
