## 2. External practice (what the big projects do, and what transfers to proot/Termux)

### 2.1 Compiler perf trackers
- **rustc-perf / perf.rust-lang.org**: default metric is `instructions:u` because it has the least variance; wall-time "is pretty much unusable for comparing small changes"; cycles in between. Significance = IQR fencing over the metric's *historical* deltas: significant when `> Q3 + 3*IQR`; magnitude = how far past the fence x percent change; relevance from count x magnitude (many 0.2 % moves = significant, one 0.4 % = not). Sources: [rustc-perf comparison-analysis.md](https://github.com/rust-lang/rustc-perf/blob/master/docs/comparison-analysis.md), [Rust internals: why instructions:u](https://internals.rust-lang.org/t/what-is-perf-rust-lang-org-measuring-and-why-is-instructions-u-the-default/9815), [Nethercote Oct 2022](https://nnethercote.github.io/2022/10/27/how-to-speed-up-the-rust-compiler-in-october-2022.html), [Kobzol on the suite](https://kobzol.github.io/rust/rustc/2023/08/18/rustc-benchmark-suite.html).
  - Transfer: **no PMU under proot** (SPEEDUP-ANALYSIS.md:7-8, "no PMU under proot"), `perf` not installed, so `instructions:u` is unavailable. The bebop analogue of a low-variance count is what T63 already calls the "primary column": **counted words / swpmu step counts / loop-span words** (bench_pinned.sh:60-66 `words_per_iter`), which are exact and noise-free. Use exact counts as the gate and ms as the report — same philosophy, different counter.
- **LLVM LNT + llvm-test-suite**: `--multisample N`, disable frequency scaling, kill background services; min/max are poor aggregators, LNT keeps all samples and learns which tests are noisy. Sources: [LNT tests](https://llvm.org/docs/lnt/tests.html), [test-suite guide](https://llvm.org/docs/TestSuiteGuide.html), [Beyls 2015 slides](https://llvm.org/devmtg/2015-10/slides/Beyls-AutomatedPerformanceTrackingOfLlvmGeneratedCode.pdf), [llvm-dev noisy results](https://lists.llvm.org/pipermail/llvm-dev/2017-February/110537.html).
  - Transfer: cannot disable frequency scaling (governor `walt`, sysfs read-only for us, no root); can only *record* the frequency and *invalidate* a run.
- **Zig gotta-go-fast**: one dedicated box, every master commit, 5 s per benchmark, records wall, peak RSS, instructions, cycles, cache/branch stats via perf syscalls; discards best and worst wall run; a single CSV atomically swapped, static HTML reads it. Source: [ziglang/gotta-go-fast](https://github.com/ziglang/gotta-go-fast), [ziglang.org/perf](https://ziglang.org/perf/).
  - Transfer: the CSV-plus-static-reader design is exactly the right weight here (python3 + one CSV under bench/).
- **Go benchstat**: median + Mann-Whitney U (non-parametric because benchmark samples are multimodal), no outlier rejection, >= 10 runs, geomean summary, warns when samples are too few. Source: [benchstat](https://pkg.go.dev/golang.org/x/perf/cmd/benchstat), [bwplotka on benchstat](https://www.bwplotka.dev/2024/go-microbenchmarks-benchstat/).
  - Transfer: python3 stdlib has no Mann-Whitney; a median + MAD rule (or a 3-line rank-sum) is enough for N=11.

### 2.2 Alerting on a time series (sheriffing)
- **Mozilla Perfherder**: per data point, Welch t-test between a back window (min 12, max 24 points, linearly weighted toward recent) and a fore window (12 points); alert when `t > 7` AND the point's t exceeds its neighbours AND the percent change exceeds the framework threshold (default 2 %, Dromaeo 5 %, AWSY 0.25 %, installer size >= 100 KB); sheriffs then triage; "low value" alerts = magnitude too small relative to the test's noise. Sources: [treeherder perfalert/__init__.py](https://raw.githubusercontent.com/mozilla/treeherder/master/treeherder/perfalert/perfalert/__init__.py) (`min_back_window=12, max_back_window=24, fore_window=12, t_threshold=7`), [perf-sheriffing docs](https://firefox-source-docs.mozilla.org/testing/perfdocs/perf-sheriffing.html), [Mozilla dataset paper 2503.16332](https://arxiv.org/html/2503.16332v1).
  - Transfer: at 20-50 commits/day (git log: 41/40/53 commits on 09-02/04/05) a 12-point back window is one day of history; the same t-test is ~15 lines of python3. But the fore window means an alert fires 12 commits late — fine for a report, wrong for a gate. For the gate use a same-session interleaved A/B against the previous fixpoint (rustc-perf's "try" comparison) and keep the windowed t-test for the trend report.
- **criterion.rs**: warmup until `warm_up_time`, Tukey fences 1.5 IQR (mild) / 3 IQR (severe) — flagged, never dropped; bootstrap CIs; a change inside +/-1 % (configurable `noise_threshold`) is ignored. Source: [criterion analysis](https://bheisler.github.io/criterion.rs/book/analysis.html).
- **hyperfine**: >= 10 runs and >= 3 s, `--warmup N`, statistical outlier warning (Tukey), `--prepare` for cache state, shell-spawn overhead subtracted. Source: [sharkdp/hyperfine](https://github.com/sharkdp/hyperfine). Not installed here; its whole method is ~30 lines of python3 (bench_pinned.sh:42-58 already has it).
- **Chromium android-binary-size trybot**: mandatory CQ bot since 2018, SuperSize symbol diff per CL, hard assertion with a `Binary-Size:` footer to override, plus a size sheriff on the telemetry alerts. Sources: [android_binary_size_trybot.md](https://chromium.googlesource.com/chromium/src/+/master/docs/speed/binary_size/android_binary_size_trybot.md), [apk_size_regressions.md](https://github.com/chromium/chromium/blob/main/docs/speed/apk_size_regressions.md), [tools/binary_size](https://chromium.googlesource.com/chromium/src/+/master/tools/binary_size/README.md).
  - Transfer: bebop already has the override-footer idea (word_budget.txt lines "added by the same commit", D11-F). What is missing is the *whole-binary* number and the per-fn symbol diff — and tools/check_abi.py:fn_starts + `fn (\w+)` order (pcprof.sh:22-24) IS a symbol table, so a per-fn size diff of bebop.bin is ~20 lines. bloaty is not installed and is ELF-oriented; the .bin is a raw word stream, so bloaty would not help anyway.

### 2.3 Latency distributions
- p50/p95/p99 over >= 31 runs; HDR histograms and coordinated-omission correction matter for *closed-loop load generators*, not for a compiler invoked N times sequentially — every run here is a fresh process and no stall is skipped, so plain sorted percentiles (aggregate.py:5-8 `pct`) are honest. Sources: [ScyllaDB on coordinated omission](https://www.scylladb.com/2021/04/22/on-coordinated-omission/), [mechanical-sympathy thread](https://groups.google.com/g/mechanical-sympathy/c/icNZJejUHfE/m/BfDekfBEs_sJ). Where it DOES apply: the store's durable-commit and reopen rows (sbench.sh:38) if they are ever driven at a target rate.

### 2.4 Memory
- `ru_maxrss` from `wait4` == VmHWM (peak RSS, KB) without the /proc race — bench_pinned.sh:47 already does it; `/proc/PID/status` VmHWM/VmRSS is readable here (probed: VmHWM 6536 kB for the probe shell) but needs the process alive; `/proc/PID/smaps_rollup` gives Pss (probed: Rss 5976 / Pss 5163 kB) — irrelevant for single-process .bins (nothing shared but the seed pages). `/usr/bin/time -v` is **not installed** (`ls /usr/bin/time` fails); python3 `os.wait4` covers it. cgroup v2 memory.peak is **not exposed** in this proot.

### 2.5 CPU time
- `ru_utime/ru_stime` from `wait4` are real kernel values (probed: a python child wall 0.102 s, utime 0.079, stime 0.004, minflt 885). **`/proc/stat` and `/proc/loadavg` are static files bind-mounted from proot-distro's `sysdata/` (dated Aug 11, 25 and 1278 bytes; mountinfo shows the sysdata binds)** — anything that reads system-wide CPU (`top`, `vmstat`, load average) lies. `/proc/cpuinfo` and `/proc/<pid>/stat` are real. Cores used = utime/wall ratio per process; the parallel scripts (std_par, battery) can sum children's rusage via RUSAGE_CHILDREN only if they wait for them — bash `times` builtin gives cumulative children utime/stime at the end of a script for free.

### 2.6 Energy on Android/Termux
- Real sensors: `/sys/class/power_supply/battery/{current_now,voltage_now}` (uA/uV) sampled over a fixed workload; `dumpsys batterystats` via adb; Termux:API's `termux-battery-status` (JSON incl. `current` in uA) — needs the Termux:API app + package. Sources: [AOSP measure device power](https://source.android.com/docs/core/power/device), [Scott Logic Android energy](https://blog.scottlogic.com/2024/05/01/measuring-android-energy-use.html), [android-platform units thread](https://groups.google.com/g/android-platform/c/bFLWckViUjk), [termux-api issue 267](https://github.com/termux/termux-api/issues/267).
- **Probed here: `/sys/class/power_supply` is Permission denied inside the proot (SELinux, app uid); `termux-battery-status` is not installed (`/data/data/com.termux/files/usr/bin/termux-battery-status` absent; Termux's `am` is on PATH, so the Termux prefix is reachable — installing the Termux:API app + `pkg install termux-api` on the Termux side would give ~1 sample/s of `current`, which is too coarse for a 1.5 s compile but fine for a 60 s fixed workload).** RAPL is Intel-only; ARM SoCs expose energy only through vendor hwmon/SCMI, none visible here. Sources: [Weaver RAPL support](https://web.eece.maine.edu/~vweaver/projects/rapl/rapl_support.html), [kernel powercap](https://kernel-internals.org/power/power-capping/).
- Therefore the only always-available energy signal is a **proxy: sum over samples of utime_slice x P(core class, freq)**, i.e. CPU-seconds on A78 at the recorded `scaling_cur_freq`. With no calibration table it degrades to "A78 CPU-seconds at frequency f" — still a monotone proxy that catches "it now burns 3x the CPU for the same result", which is all a compiler needs. Leave the calibration knob (mW per class per freq bin) as a one-line table to fill if a Termux:API current sample ever becomes available.

### 2.7 Noise control on big.LITTLE (this box)
- Pinning works and is verified (bench_pinned.sh:23-24, Cpus_allowed_list; cpu 7 refuses taskset per ROADMAP.md:159).
- **Frequency is readable and NOT fixed**: `/sys/devices/system/cpu/cpu4/cpufreq/scaling_cur_freq` was 2054400 then 1651200 kHz within a minute (max 2400000, governor `walt`); `cpufreq/stats/time_in_state` is readable (per-freq residency counters — a *cumulative* record of how much of a run sat at which frequency: read before/after, diff = exact freq histogram of the run, zero sampling cost).
- **Thermal is readable**: `/sys/class/thermal/thermal_zone{7..21}` types `cpu-1-0..cpu-1-7` (big cluster sensors, 41-50 C now), `cpuss-0/1`, millidegrees. A guard "big-cluster max temp < X and freq >= 2.0 GHz before AND after the sample, else mark INVALID/RETRY" is two `cat`s.
- Method points that transfer from LNT/rustc-perf/benchstat: interleave A and B runs (ABAB…) so drift hits both; median over >= 11 for gates, p95 as report; min-of-N is defensible for a *deterministic* compile on an otherwise idle core (min = least-disturbed run) but median is what every listed project uses — use median for the gate and print min too. Do not reject outliers, record them (criterion, benchstat). boxguard's 450 % CPU cap and the always-on fuzzd on the LITTLE cores mean a perf sample must also record `ps` count / whether a chain is running; single-run numbers are worthless on this box (DEV-LOOP.md:24-25).

## 3. Menu of concrete evals

Common substrate for every item (so they do not each reinvent it): one python3 helper `tools/perf.py` (~150 lines) that (a) runs `argv` N times pinned via `taskset -c $CORE`, using `os.wait4` for wall/utime/stime/maxrss (the code is bench_pinned.sh:42-50), (b) reads `scaling_cur_freq` + max big-cluster temp + `cpufreq/stats/time_in_state` before/after, (c) appends rows to **`bench/perf.csv`** (`ts,commit,bin_md5,metric,unit,n,median,min,p95,mad,core,freq_khz_min,temp_mc_max,valid,note`), and (d) prints one journal line in the H:/DID:/GOT:/VERDICT: format for docs/exp.journal. CSV over sqlite: git-diffable, `cut`/`awk`-able, and sqlite3 can `.import` it any day (`python3 -c "import sqlite3,csv"`). Baseline for gates = the previous fixpoint bebop.bin (git shows it: `git show HEAD~1:bebop.bin`), run **interleaved** in the same session (ABAB), never a stored number.

Threshold rule used below unless stated: **median of N; regression if delta > max(T%, 3 x MAD_rel of the baseline series)**, where MAD_rel = MAD/median. T is per metric. Both conditions guard: T% against a noisy metric, 3 MAD against a quiet one.

## 4. Recommended minimal bundle and build order

1. **E7 guard + `tools/perf.py` substrate** (wait4 + sysfs stamps + CSV + journal line) — everything else is a caller of it, and without the validity stamp every other number on this box is a single-run anecdote.
2. **E1 self-compile trend (with E5 maxrss and the E6 cpu-seconds proxy, which are free)** — the one metric the operator already tracks by hand in three places (DEV-LOOP.md, ROADMAP.md:162-163, honest.sh K5) and the one with the worst history (292 s → 1.5 s, an unexplained 2.7x drift).
3. **E3 size trend with budget** (bebop.bin + stub + per-fn words) — exact, zero cost, turns 44-line budget commits into one line and gives the compiler's own growth curve.
4. **E2 K-kernel interleaved A/B** — makes T83's MET/UNMET and ROADMAP's "K4 <= 3.0 ms" an asserted exit code instead of a hand-pasted table.
5. **E11 report generator** last, hooked to the end of chain.sh, so the four CSV producers get one reader; E12 bisect is a 20-line wrapper once E1/E3 exit codes exist.

Reasoning: every item reuses code that already exists (bench_pinned's wait4 loop, honest.sh's kernels, check_abi's fn table, construct_parity's budget grep); the order goes exact-and-free (size, validity) before noisy (ms); cpu-time and energy fall out of wait4 for nothing; nothing needs a new dependency or a change to bebop.bp; the whole bundle adds ~60 s to a chain that already takes 94-123 s.

## VERDICT
- Today only size (constructs, census) and correctness are gated; performance/latency/memory are hand-run reports, cpu-time and energy are unmeasured, and no metric is a per-commit series a script can read back.
- The box allows: pinned wait4 (wall/utime/stime/maxrss), sysfs cpufreq + thermal (readable, not controllable), and exact word counts; it denies PMU, RAPL, power_supply, /proc/stat, /usr/bin/time, and any governor control.
- Best transferable practice: exact counts as the primary (gate) column like rustc-perf's icounts, median-of-N interleaved A/B for ms with a 3 %-or-3-MAD rule, Perfherder-style windowed t-test only for the trend report, Chromium-style budget footer (already D11-F) extended to the whole binary, Zig-style single CSV + static reader.
- Build E7 → E1(+E5,E6) → E3 → E2 → E11; ~400 lines of python3/bash total, +~60 s per chain, no new dependencies, no edits to bebop.bp.
- Energy stays a proxy (A78 CPU-seconds x freq) unless the operator installs Termux:API on the Termux side; say so in the column header rather than pretend.
